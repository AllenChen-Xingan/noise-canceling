## 二、为什么先做这个（只在本线范围内比）

1. **零上线代价**：延迟、占用、导出流程都不变，是四条路里唯一不碰 45 ms 线的【推断】
2. **rl 的结论也是先监督微调**：能写成可微形式的检查项直接进损失，这一步拿到强化学习想要的大部分【029 第 73 行，标「假设」】
3. **算力够**：第一个实验每组 5,000 步，在本机 MPS（带绕法）上约 1.2 小时训完【实测单步 + 推断】
4. **主要卡在数据，不在算法**：本机能合法训练的数据覆盖不了弱场景（第六节），这一点四条路都绕不开

### 3.1 起点与超参

| 项 | 取值 | 依据 |
|---|---|---|
| 起点 | 官方 `model_trained_on_dns3.tar` | 成绩单上的 GTCRN 就是它 |
| 优化器 | Adam，梯度裁剪 3.0 | SEtrain 模板配置【出处 M2 `train.py:70` · `cfg_train.yaml:63`】；本表「官方」都指 SEtrain 模板，不等于官方检查点的实际训练历史（未核）【codex 027 第 6 轮 #2】 |

| 设备 | MPS + `mps_fix.py`；绕法失效时退回 CPU | 【实测，第七节】 |

### 3.2 损失：官方损失 + 4 项

`L = HybridLoss + w_lvl·L_lvl + w_on·L_on + w_sp·L_sp + w_kd·L_kd`

| 项 | 管什么 | 写法 | 依据 |
|---|---|---|---|
| HybridLoss | 锚点 | 官方原样：30 ×（压缩复谱 MSE）+ 70 ×（压缩幅度 MSE）+ SI-SNR | 【出处 `resources/gtcrn/loss.py:16-30`】 |
| L_lvl 人声被压低 | GTCRN 有 12% 的段人声被压低超过 3 dB（DFN3 3%），多在食堂 · 共享办公 · 车厢 | 只在主说话人单独说话的帧上：输出投影到干净人声的能量 ⟨o,c⟩²/‖c‖² 与干净能量比，换成 dB；罚 `relu(下降 dB − 2)`。2 dB 比否决线（−4 dB，D85）留 2 dB 余量 | 写法照 V-SPLVL（`src/eval/src/verifiers/perceptual.rs:263-291`）；12% 来自【实测 029 第 53 行】；**2 dB 余量与 relu 形式：我们自定，待实验** |
| L_on 字头 | 只奖励多压会多吞字头 | 字头 = 静了 ≥ 100 ms 后重新开口的前 50 ms；罚「字头损失 − 整段有声损失」超出 0 的部分（单边）。和 V-ONSET 同一个定义 | 写法照 V-ONSET（`perceptual.rs:119-172`）；单边（只罚压过头）的思路来自不对称损失【出处 M8 式 2–3】；**用 V-ONSET 的定义直接当损失：我们自定，待实验** |
| L_sp 拉回原权重 | 防遗忘 | `λ·‖θ − θ_DNS3‖²`（L2-SP） | 【出处 M4 式 5（EWC 式）· M5（L2-SP λ = 1e-4）】 |
| L_kd 原模型当老师 | 防遗忘 | 只在回放批上：微调版输出与原检查点输出的压缩复谱 MSE | 【出处 M5（一致性 λ = 0.1）】 |

**权重怎么定**（我们自定，待实验）：
1. 先在原检查点上过 200 个开发批，量出每项的大小；把 w_lvl、w_on 设成「初始时各占 HybridLoss 约 10%」，w_kd 从 0.1、λ 从 1e-4 起【出处 M5 的起点】
2. 4 项各扫 3 档（× 0.5 · × 1 · × 2），每档训 1,000 步：共 12 次 × 约 14 分钟 ≈ MPS 2.9 小时（CPU 约 4.6 小时）【推断：实测单步 × 步数】
3. 选法：在**开发份**上，选「字头超额与人声压低都不比原检查点差」里降噪量最大的那档。开发份 = 第六节第 5 条切分表里的「开发」那一块（只此一处定比例），**不用评测集选**——评测集一旦参与调参就不再是独立裁判（D57；exp006 曾用报告集扫参，教训见 `docs/experiments/exp006-scene-sim/README.md` 第 53 行）

**交叉校验**（CLAUDE.md 第五节 5 条）：L_lvl、L_on 是 V-SPLVL、V-ONSET 在 Python 里的第二处表示。实现时必须加三条测试【codex 027 第 6 轮 #1】：
1. **对拍用实际参与反传的那份代码**：几段固定音频上，可微实现的前向值（换成 dB 后）与 Rust verifier 的读数一致（容差另定），对不上就红。不另写一份「不可导版本」去对拍——那样可微版本写错也能过
2. **梯度检查**：小输入上用有限差分核对可微实现的梯度
3. **样本不足时的规则**：verifier 在字头少于 3 个、主说话人单独说话不足 0.5 s 时读「待测」（`perceptual.rs:132-138` · `:278-280`）；训练里同样条件下该项**跳过、不计入分母**（按批里有效段数归一化），整批都无效时该项为 0。权重标定（上面第 1 步）只用有效段算初始大小；如果原检查点上某项初始值本来就是 0（没有超出），按「超出 1 dB 时等于 HybridLoss 的 10%」标定，而不是除以 0

**讨好风险**：损失里直接用了验收时要看的两个定义，模型可能学会「骗过这两个读数」而不是真的保住字头。所以验收另看不进损失的几项：V-WEAK（轻声字）、V-EAT-ASR（吃字）、V-TIMBRE（音色）和人耳（第四节）【推断】。

### 3.3 不做的

- 评分模型（SCOREQ · Distill-MOS · DNSMOS）不进损失：D81 第 4 条；029 实测它们也偏爱「多压」
- 冻层或只加低秩适配器：48K 参数的模型能不能这样学到够，未量化；留作第一个实验失败后的备选【出处 M6 有 89k 参数的成功例子】

## 四、验收：两种口径

引擎在模型后面混回原声：说话时约一半是原声（−6 dB），停顿时约 1/4（−12 dB）【读源码 `src/engine/src/engine.rs` `mix_out`；cands notes 第三节实测 m 中位数 0.501】。所以成绩单上模型本身的进步会被冲淡；冲淡多少**未量化**——混回系数由引擎按模型输出算，微调后会变，ESTOI 与 dB 类指标也不随波形线性缩放，只能两种口径分别实测【codex 027 第 2 轮 #4】。

| 口径 | 怎么跑 | 用来 | 各量哪几项 |
|---|---|---|---|
| A · 用户听到的（判合格） | v2 成绩单，默认 `safety: true` | **唯一的合格判据**：用户听到的就是它 | 全部 v2 项，重点看下表；另记原版与微调版的混回系数 m 分布（每 10 ms 最小二乘拟合，同 cands notes 第三节的做法），只报不判 |
| B · 模型本身（只诊断） | 同一场景集，`safety: false` | 看模型到底变了多少；A 没变好时判断是「模型没学到」还是「被混回压平了」 | ESTOI · 降噪量 V-NR · 字头 V-ONSET · 背景跳变 V-BGSTAB · 人声被压低 V-SPLVL（只报纯模型指标；这个口径下混回整个关掉，量不到混回系数）。混回系数 m 的分布（原版 vs 微调版）在**口径 A** 里另记【codex 027 第 5 轮 #2】。**不预测 A 与 B 的倍数关系**：m 由引擎按模型输出算（`engine.rs` `mix_out` 里 `env.process(&self.wet, …)`），微调后 m 本身会变，ESTOI 与 dB 类指标也不随波形线性缩放；两种口径都实测【codex 027 第 1 轮 #4】 |

口径 A 的合格线（全部用「微调版 − 原版」的配对差，按源片段成组 bootstrap 区间，D85 G-1）。**区间宽度：开发评测 95%；终测 97.5%**（终测最多 2 次，5% 误报率平分，见第五节）【codex 027 第 4 轮 #2】：

| 类别 | 评分项 | 线 |
|---|---|---|
| 要涨 | V-ESTOI（目标场景合并） | 均值 ≥ +0.01，区间下界 > 0 |
| 要涨，但不单独算数 | V-NRMOS-DISTILL 与 V-NRMOS-SCOREQ | 两者都 ≥ +0.05（D81：两个评分模型都说好才算好）；只有它们涨、ESTOI 不涨 → 不合格 |
| 不许退（全部 60 个场景任务，重点是 71 组守住项） | V-ONSET · V-BGSTAB · V-TIMBRE | 退步区间上界 ≤ R-2 容许量（建议 1 · 2 · 1 dB，029 待人定） |
| 不许新增否决 | V-SPLVL（−4 dB）· V-EAT-ASR（单段多错 ≥ 5 字）· 坏值 | **按片段 ID 比**：微调版的否决片段集合必须是原版的子集（修好一段不能抵消毁掉另一段）；坏值段数必须为 0；「待测 / 读不出」不算过，单列并逐段说明【codex 027 第 1 轮 #2】 |
| 其余场景 | 全部 v2 项 | 不新增「不过」 |
| 人耳 | 目标场景 + 守住项各挑最差 2–3 段 | 盲听，结果回灌（D44）；机器判据和人耳冲突时以人耳为准 |

- **两份评测，用法不同**【codex 027 第 1 轮 #1 · 第 2 轮 #1】：
  - **开发评测 = 现有 exp013 场景集**：每个冻结候选上一次，结果可以用来决定下一步（加数据、加步数、调 w_on）。正因为它会反馈，它**不再当最终裁判**
  - **终测 = 新留的独立场景集**：同一份 `scenes.json` 配方，素材全部来自各数据集训练份里划出的**终测原料池**（第六节第 5 条），从没进过训练、开发、开发评测；**不用 D63 测试份**——D63 规定测试份不进任何合成原料，而终测场景是合成的【codex 027 第 4 轮 #1】。生成归场景集负责的线；终测在冻结最终候选之后**只跑一次**，跑完不再按它改模型。如果终测不过，这个候选就不过；再训出的新候选要再留一份新的终测（素材另切），不能复用
  - **终测次数与显著性预算预先定死**【codex 027 第 3 轮 #1】：这条路线（GTCRN 微调）最多上 **2 次**终测；总误报率 5% 按 Bonferroni 平分，每次终测「要涨」那一项用 **97.5%** 区间（单次失败率预算 2.5%）。每次终测的结果（过或不过）都记进实验清单，不删。2 次都不过 → 停，交人定是否换路线，不再开第 3 份终测
  - **终测素材逐类映射**【codex 027 第 3 轮 #2】：终测要覆盖 exp013 用到的每类素材，且每类都不能和训练、开发、开发评测重叠。第一批只能覆盖一部分：

| exp013 用的素材类 | 终测用什么 | 第一批能不能覆盖 |
|---|---|---|
| 英文语音（LibriSpeech test-clean 奇数位） | LibriSpeech dev-clean / test-other | 能（A5） |
| 中文语音（本机 6 段 Commons 朗读） | AISHELL-3 的终测原料池（第三批 C1） | **不能**——缺口 |
| 真实环境底噪（DEMAND 后 40%） | QUT-NOISE 终测原料池（咖啡馆 · 车内 · 街道 · 家居） | 部分：开放办公、食堂等没有对应 |
| 车内 · 地铁 · 候车厅底噪（DEMAND TCAR / TMETRO / PSTATION） | CochlScene 终测原料池（第二批 B1）。DEMAND 这三个环境的前一半是 exp013 定的「只测、不当任何合成原料」测试份，不用 | **不能**——缺口 |
| 突发声音（ESC-50 每类 12 段） | ESC-50 其余片段（NC 只评测不训练，D64；拿来合成评测场景照 exp013 先例；本机只有 168 段，全集大小约 0.6 GB 未核）或 FSD50K 训练份里划出的终测原料池 | **不能**——缺口 |
| 合成声音（本线自写） | 同一套合成代码换种子空间 | 能（代码不是数据，只是种子不同） |
| 背景音乐（Maple Leaf Rag） | 另一首公有领域录音 | 未定 |
| 房间冲激响应（MIT · ACE · McVAMPIRE） | OpenSLR 28 终测原料池；车内冲激响应没有替代 | 部分：车内缺 |

  覆盖不全时，终测**只对覆盖到的场景下结论**，报告里列出没测的场景，不能说「全部场景合格」。补齐中文、车内 / 地铁 / 候车厅、突发声音这三类，是「全部场景合格」这一结论的前置依赖
- **失败时**：诊断回到开发份与开发评测（ESTOI 不涨先看口径 B；字头退步看开发份上的字头超额），改数据 / 步数 / w_on 后冻结新候选，再上开发评测

## 七、MPS 能不能用来训练（实测）

- **不带绕法不能用**：同一份权重和输入，MPS 前向和 CPU 差 61%，梯度差约 84%【实测，`runs/20261105-150438-parity/`】
- **根因**是 PyTorch 的 bug：逐通道、沿第一空间轴带空洞的 `Conv2d` 在 MPS 上算错（差约 100%）；转置卷积对输入的梯度内部用的是同一个算子，也错。GTCRN 中招 4 处（编码器 en_convs.3 / 4、解码器 de_convs.0 / 1）。GRU 单独比（同输入、同上游梯度，GTCRN 用到的三种尺寸）：前向、输入梯度、权重梯度都和 CPU 一致（差 < 1e-5，测试 `GruTest`）——调研 013 担心的 GRU 问题（PyTorch #94691）在这个版本、这些尺寸上没出现。逐层前向读数（`runs/20261105-150606-layers/`）只用来找第一个错的层，下游各层（含 GRU）的读数已被上游污染，不能单独说明 GRU【实测；最小复现 `smoke/test_mps_fix.py`；codex 027 第 1 轮 #3】
- **绕法**：`smoke/mps_fix.py` 把这 4 个卷积的 forward 换成数学等价的「3 个抽头各做一次无空洞卷积再相加」，参数与 state_dict 不变。带绕法后正式尺寸（8 × 4 s，20 步）前向差 1.2e-6、整模型梯度差 6.1e-5、20 步损失差 4.4e-6、训后完整状态（参数 + BatchNorm 运行统计，249 个张量）差 1.0e-4；把 MPS 上训出的状态装进**没打绕法**的原模块，CPU eval 前向与 CPU 训出的模型差 1.0e-3（线 1e-2）——导出用原模块这一步也对上了。全部过线【实测，`runs/20261105-152353-parity-fix2/`；补 BN 与导出两项见 codex 027 第 1 轮 #6】
- **局限**：①只验证了 torch 2.15.0（macOS 27.0.1 · Apple M5）；换版本先跑 `test_mps_fix.py`——上游修好时其中两条会红，提醒去掉绕法 ② 导出 ONNX 用原模块，不用绕法 ③ MPS 回落开关的截获逻辑只用合成警告文本测过，没有真实样本 ④ 带绕法的单步耗时：批量 32 时 0.856 s，比不带绕法（0.827 s）慢约 3.5%，仍比 CPU（1.372 s）快约 1.6 倍；批量 8 时 0.600 s，不如 CPU【实测，`runs/20261105-153553-step-fix/`】
