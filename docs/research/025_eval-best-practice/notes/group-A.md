## 0. 一句话结论

| 项 | 结论 | 要不要动 |
|---|---|---|
| V-NAN 坏值 | **业界没有**（工程常识），成立 | 小改：另报「超过 1.0 的样本数」（会在转 16 位时削顶），不进否决 |
| V-MUTE 静音全零 | **可对齐**（Google Works With Meet 有同类条款） | 不改算法；补一句单位换算依据 |
| V-LAT 附加延迟 | **可对齐**——6.6 ms 偏差的根因已定位：未归一化的互相关 + 2 s 窗口几乎全是噪声 | **要改**，改完重跑 V-LAT（只 2 段受影响） |
| V-FRAME 最坏一帧 | **我们有意不同**（比 DNS 挑战赛严一倍），但统计口径要补 | 改报法：报超时次数与 p99.9，不单看最大值；不进场景成绩单可保持 |
| V-SWITCH 切换跳变 | **业界没有**直接标准；最接近的是 Android OboeTester 用已知正弦测「毛刺」 | 建议改成「固定测试信号 + 强制切换」的系统层检测 |
| V-CLICK 咔嗒 | **可对齐**（思路与经典 AR 残差检测、OboeTester「与预测值比」同类） | 维持「只报不判」；补人造咔嗒检出率与人耳标注，才可转判 |

## 1. V-NAN · 坏值

代码：`src/eval/src/verifiers/physical.rs:74-91`；注册表 `src/eval/src/verifiers.rs:94-106`；成绩单否决项 `specs/rubric/scorecard.md:59`。

1. **算法**：逐样本计数 NaN / Inf，加上幅度 > 4（即 +12 dBFS）的样本。业界没有专门标准：IEEE 754 定义了非有限值，各家实时音频框架都把 NaN 当致命错误处理，但没有「测试方法」条款【推断】。我们的算法就是最直接的写法，**一致于工程常识**。
2. **参考信号**：只看输出本身，不需要参照。合理。
3. **过线口径**：任何 > 0 即否决。确定性事件，阈值 0 无需出处。
   - 但「幅度 > 4」这条混了两件事：NaN / Inf 是**数值失效**；幅度大是**削顶风险**。虚拟麦克风输出 float32，下游会议软件多半转 16 位，|x| > 1.0 就会被削顶【推断】。4.0 只抓「完全失控」，抓不到 1.0–4.0 之间的削顶。
4. **汇总**：按段计数，任何一段 > 0 即该场景否决。确定性事件，用「任一」汇总正确。
5. **统计**：确定性检测，1 次运行就够；不需要置信区间。注意它只证明「这 480 段上没出现」，不证明「不会出现」——NaN 多由极端输入（全零能量取对数、极大幅度）触发，靠的是专门的边界探针（`src/eval/src/probes.rs` 一类）而不是场景段数【推断】。

**结论：业界没有**（工程常识，成立）。
**与 012**：012 `verifiers.md:113` 写「计数；任何 > 0 → 否决；确定性」，一致。
**建议**：另加旁报字段 `over_1`（|x| > 1.0 的样本数），只报不判；V-NAN 本身不变。

## 2. V-MUTE · 静音全零

代码：`src/eval/src/verifiers/physical.rs:93-131`；阈值 `src/eval/src/thresholds/table.rs:137-145`（−90.3 dBFS、稳定期 0.3 s）。

1. **算法**：输入末尾的数字全零段，过 0.3 s 后量输出峰峰值（dBFS）。业界对应：Google「Works With Meet」音频模块要求静音时采样全零或 (max − min) ≤ 0.0028 dBFS（012 已核原文，[S35]）。我们算法与它同构（都是峰峰值）。
2. **参考信号**：输入 = 数字静音。一致。
3. **过线口径**：我们取 1 LSB@16 bit = −90.3 dBFS，理由是 Meet 原文单位口径存疑（012 已注）。−90.3 dBFS 的换算：峰峰值 2/65536 相对满量程峰峰值 2 → 1/32768 → 20·log10 = −90.3【推断，算术】。这比「全零」宽一点，但转 16 位后就是「最多抖 1 个码」，与 Meet 意图一致。
4. **汇总**：系统层事实，取 CI 层结果，不在场景里重算（`specs/rubric/scorecard.md:51`）。正确。
5. **统计**：确定性，1 次够。

**结论：可对齐**——算法已对齐；只需在注册表 anchor 里写清 −90.3 的换算式，避免读者以为是拍脑袋的数。
**与 012**：一致（012 `gap.md:48`「可对齐，加子项」，现已加）。
**遗留**：稳定期 0.3 s 仍是建议值；Meet 原文没写稳定期【二手，转引 012】。可改为「从静音开始量，同时旁报 0.3 s 后的值」，让人看见收敛过程，但不急。

## 3. V-LAT · 附加延迟

代码：`src/eval/src/verifiers/physical.rs:5-37`；互相关 `src/eval/src/analysis.rs:230-247`；预算 `src/types/src/latency.rs:12`（45 ms）、平台预算 `src/types/src/latency.rs:149-153`；运行 `src/eval/src/system.rs:278-315`。

现在的做法【读代码】：
- **判分的值是账面**：`ledger_total_ms`（引擎延迟账 + 平台预算 96 帧）≤ 45 ms。exp014 里模型都是 43.67 ms、原声直通 27.67 ms（配对差 +16 ms，`analysis.md` §3）。
- **实测只做核对**：输入前 2 s（32 000 样本）与未对齐输出做**未归一化**点积，在 0–2048 样本里取最大值；与声明相差 > 1 样本就判否决。

### 3.1 phone-booth-c07 的 6.6 ms 从哪来（实测 + 读代码）

- 6.625 ms × 16 kHz = **106 样本**。原声直通、参考降噪器、GTCRN 都偏同样的 106 样本（issue 草稿：原声直通量出 6.625、模型量出 22.625 = 16 + 6.625）。
- 我在 `phone-booth-c07-ext/mix.wav` 上重算同一公式【实测】：
  - 滞后 0 的点积 r(0) = 1.9742，滞后 106 的点积 r(106) = 1.9765，后者略大，所以取了 106。
  - 每 0.1 s 能量：前 1.5 s 都约 0.003（只有底噪），1.6–1.8 s 0.04–0.06，**1.9 s 起人声才出现（1.8）**，2.0 s 后 7.0、5.7。
  - 窗口 [106, 32106) 的能量 2.915，窗口 [0, 32000) 只有 1.974。
  - `phone-booth-c07-mba` 同样取到 106，r(0) = 2.0337 < r(106) = 2.0456【实测】。
- **根因**：点积没有归一化。x[0..n] 与 x[k..k+n] 的点积上限是两段能量的几何平均；当人声恰好在 2 s 窗口末尾起来时，往后挪 k 个样本，第二段会多吃进一截响的人声，能量变大，点积可能超过 r(0)。106 样本 ≈ 151 Hz，正是一个浊音基音周期，所以落在基音周期上的次峰被「能量增长」抬过了主峰【实测 + 推断】。
- 归一化后，滞后 106 处的相关系数只有 0.824，而滞后 0 恒为 1.0【实测】。也就是说**换成归一化互相关，这两段就不会错**。
- 全 480 段扫描（同一公式，原声直通情形 = 输入的自相关）：见 §3.6。

### 3.2 五问

1. **算法**：
   - 3GPP TS 26.132 §8.10.1 / §7.10.1（发送方向延迟）：用 ITU-T P.501 的复合源信号（CSS，含伪随机噪声段，噪声段必须长于最大预期延迟，建议 48 kHz 下 32k 样本）；对测得信号与原信号做互相关，取**互相关包络**的最大值；扣除测试设备自身延迟【二手·镜像】。
   - TS 26.132 §7.10.4.2（接收方向、用真实语音）：**每句话一个 4 s 矩形窗、窗心对准这句话**，每窗取包络最大值，一句得一个延迟值，报 40 句里去掉最大 2 个后的最大值（约第 95 百分位）【二手·镜像】。
   - TR 26.954 §5.1（回声法）：分析窗从 50 ms 后开始，避开耦合与侧音峰【二手·镜像】。
   - 业界共同点：**用能量充足、自相关尖锐的测试信号**（CSS 的伪随机段），或**把窗放在说话的地方**；看包络而不是原始相关的正峰。
   - 我们的不同：① 窗固定在每段开头 2 s，不管有没有人声（多数段开头是噪声垫场）；② 未归一化；③ 取正峰而非包络 / 绝对值；④ 用场景段而不是测试信号。①② 合起来就是 c07 的根因。
2. **参考信号**：业界用原始测试信号（CSS / 干净语音）当参照。我们用带噪输入 `mix` 对输出：降噪器把噪声去掉后，噪声部分与输出几乎不相关，峰值只靠人声撑——开头 2 s 若人声很少就不稳【推断】。对「算法延迟」这种确定性的数，最好的参照是**专门喂一段测试信号**（干净语音或 CSS 结构的信号）给同一处理代码，与场景无关【推断，依据同上 3GPP 条款】。
3. **过线口径**：45 ms 出自 D32（我们自定的部件预算）。外部对照（012 已核）：G.114 §4「嘴到耳 < 150 ms 大多数应用基本透明」，不是硬线；TS 26.131 §6.11.1 收发合计 150 / 190 ms；DNS 挑战赛实时赛道算法延迟 ≤ 40 ms（帧长 + 帧移 + 前瞻，arXiv 2009.06122 §2）【读原文】。我们 45 ms 是整条链（含 IO、重采样预算），和 DNS 的 40 ms（只算算法）不是同一口径，不能直接比；把我们的「模型算法延迟」单拿出来是 16 ms，远在 DNS 线内【推断】。
4. **汇总**：现在按段判，任一段核对失败就让整场景否决。业界：TS 26.132 是**每次通话一个值、≥ 5 次取最大**（因为真机有帧同步抖动，最大可差 20 ms）；语音法取第 95 百分位【二手·镜像】。我们离线、确定性，延迟不随段变，**本该是一个系统层的数**，像 V-MUTE 那样在 CI 层量一次，而不是在 480 段上各判一次。
5. **统计**：真实延迟是确定性的，不需要样本量；需要统计的是**测量器本身的失败率**：478/480 段量准，2 段量错（同一录音的两路麦）【实测，exp014】。注册表写「5 个种子各量一次（Teams §6.35 放 5 次）」——Teams 放 5 次是为了抓真机每次通话的抖动，我们的实现确定性，5 次必然一致，**这个引用起不到作用**，应删掉对齐 Teams 的说法，改写「离线确定性，1 次即可」【读代码 + 推断】。

### 3.3 结论

**可对齐**。改法（按优先级）：
1. **测量器**：互相关改为**归一化**（除以两段能量的几何平均），并取 |相关| 或 Hilbert 包络的最大值；窗口不再固定开头 2 s，改为整段或「人声活动最多的 2–4 s」（照 TS 26.132 §7.10.4.2 窗心对准句子的做法）。
2. **口径**：算法延迟改成**系统层检测**：每个系统用一段固定的测试信号（干净语音 + 一段白噪声 / 伪随机段，仿 P.501 CSS 结构）量一次，进 CI；场景段上的互相关降为旁报诊断，量不准时判「不知道」，不再判否决。
3. **兜底**（issue 草稿已提）：原声直通在同一段也对不上时，判「不知道」。有了第 1 条，这条只是保险。
4. 删掉「5 个种子 = Teams §6.35」的对齐说法。

**与 012 不同**：012 `gap.md:30` 结论是「可对齐：换 P.501 CSS、放 5 次报平均与最大」。这次同意换测试信号，但**不同意「放 5 次」**——原因：我们离线确定性，重复无信息；真正的风险是测量窗与归一化（012 没覆盖，c07 是之后才暴露的）。另外 012 说宽带 §8.10.1 未核，这次在镜像上核了：发送方向同样是 CSS + 互相关最大值 + ≥ 5 次取最大【二手·镜像】。

## 4. V-FRAME · 最坏一帧耗时

代码：`src/eval/src/verifiers/physical.rs:39-72`；计时 `src/eval/src/system.rs:292-295`（每 hop 用 `Instant` 包住 `Engine::process`）；阈值 `src/eval/src/thresholds/table.rs:130-135`（最大 ≤ 0.5 个周期）。不在场景成绩单表里（`specs/rubric/scorecard.md` 第三节没有这一行）。

1. **算法**：
   - DNS 挑战赛（ICASSP 2021）实时赛道：处理一帧（帧长 T）的时间必须**小于帧移 Ts**，基准机是 Intel Core i5 四核 2.4 GHz（arXiv 2009.06122 §2「Track 1」）【读原文】。原文没写是平均还是逐帧最大；参赛者普遍报平均实时因子（RTF）【推断】。
   - 实时音频工程的通行看法：一次超时就是一次可听的掉音（Android OboeTester 把 XRun 计数和毛刺对应，见 §5 来源）【读原文·文档】。所以真正该数的是**超时次数**，而不是均值。
   - 实时系统领域：最坏执行时间（WCET）靠测量得到时，单次最大值不稳，学界用「测量 + 极值统计」（MBPTA）给出超时概率【摘要】。
   - 我们：逐 hop 计时、取最大 ÷ 周期，旁报 p99.9。思路对（看尾部），但只有「最大」进判定。
2. **参考信号**：hop 周期（= 墙钟预算）。一致。
3. **过线口径**：我们 ≤ 0.5 周期，比 DNS 的 < 1 周期严一倍。理由合理：输入输出线程、重采样、跨进程环也要占同一周期，模型不能独占【推断】。这是**有意不同**，应在 anchor 写清。
4. **汇总**：现在每段取最大。最大值受操作系统调度、首帧缓存冷启动影响大，单段最大值是噪声很大的统计量【推断】。建议：
   - 去掉每段第一个 hop（冷启动）后再统计，或单列「首帧」；
   - 判定用「**超过 1 个周期的次数**」（= 真掉音）为否决、「p99.9 ≤ 0.5 周期」为过关；最大值只报不判。
5. **统计**：
   - 「超时次数 = 0」想要有意义，用「三法则」：0 次超时时，超时率 95% 上界 ≈ 3 / 总 hop 数。要证明超时率 < 1e-4（每 100 秒最多 1 次，按 10 ms hop），需要 ≥ 3 万个 hop ≈ 5 分钟音频【推断，算术】。exp014 有 480 段 × 12 s ≈ 96 分钟，够。
   - p99.9 要估稳，经验上至少 10 / (1 − 0.999) = 1 万个样本【推断】；单段 12 s 只有约 750–1200 个 hop（hop 10–16 ms），**单段的 p99.9 就是第 1–2 大的值，和最大值差不多**——所以要把整批 hop 合在一起算，而不是按段。
   - 计时环境：已有「CI 虚拟机 / debug 构建不过线时判『不知道』」；还应记录电源状态（电池降频，见用户记忆「Mac 测速三个坑」）。

**结论：我们有意不同**（阈值比 DNS 严，理由成立）+ **可对齐**（汇总与统计口径要改）。
**与 012 不同**：012 `gap.md:46` 写「DNS 实时赛道 RTF ≤ 0.5（平均）」「已对齐（更严）」。原文是「处理时间 < 帧移 Ts」，例子里 Ts = T/2 是**帧移等于半个帧长**，不是「RTF ≤ 0.5」。原因：012 把「Ts = T/2」误读成了 0.5 的实时因子【读原文】。我们 0.5 周期仍然比 DNS 严，结论方向不变，但出处要改。

## 5. V-SWITCH · 送原声切换跳变

代码：`src/eval/src/verifiers/physical.rs:133-174`；阈值 `src/eval/src/thresholds/table.rs:147-152`（≤ 2 倍）。不在场景成绩单表里。

1. **算法**：在每次进出送原声（旁路）的点 ±64 样本内，取输出一阶差分最大值，除以输入一阶差分的 p99.9。
   - 业界没有「旁路切换跳变」的专门测试条款。TS 26.132 的「切换特性」指双讲时的衰减切换，不是同一件事【二手·镜像，目录级】。
   - 最接近的做法：Android OboeTester「毛刺测试」——播放已知正弦，锁相预测下一个样本，实际值偏离预测超过容差（默认 0.1）就记一次毛刺；后来为防降噪等效果滤掉正弦，加了扫频与多音信号【读原文·文档 / PR】。也就是：**用已知测试信号 + 与预测值比**，而不是用自然语音的差分统计。
2. **参考信号**：我们用输入自身差分的 p99.9 当分母。问题：输入有瞬态时分母变大、检测变松（注册表已自认）；而且切换点落在静音或人声不同位置，结果随段变化【读代码】。
3. **过线口径**：≤ 2 倍，建议值，无外部出处。012 原定「跳变 = 0」。
4. **汇总**：每段取最坏；没发生切换判「不知道」。合理。
5. **统计**：给定输入和切换时刻是确定性的；但「切换落在什么样的信号上」是随机的——要覆盖最坏情况（切换落在大幅度低频浊音上），自然语音场景需要很多段才碰得到【推断】。用固定测试信号可以把它变成 1 次就够的确定性检测。

**结论：业界没有**（无直接标准），可借 OboeTester 的思路做成确定性检测。
**建议**：
- 新增系统层检测：喂 1 kHz 正弦（或 200 Hz + 1 kHz 双音、扫频）以 −12 dBFS，**强制**在不同相位上切换 N 次（例如 8 个相位 × 进出各 1 次），量「输出与理想交叉淡化结果的最大偏差」；过线用绝对值（如 ≤ −40 dBFS，建议值，待定标）。
- 场景段上的 V-SWITCH 保留为旁报。
**与 012**：012 `verifiers.md:114`「切换点采样跳变；跳变 = 0；确定性」。这次的不同：「确定性」只在**固定测试信号**下成立，在场景段上不成立；建议回到 012 的「确定性」本意，换输入而不是放宽阈值。

## 6. V-CLICK · 爆音 / 咔嗒

代码：`src/eval/src/verifiers/speech.rs:143-159`（局部 MAD 离群）、`:161-`（干净轨残差）、`:202-262`（判定与每分钟计数）；阈值 `src/eval/src/thresholds/table.rs:228-`（0 个/分钟、k = 8、残差占比 0.5）。成绩单「只报不判」（`specs/rubric/scorecard.md:67, 90, 142`）。

1. **算法**：
   - 学界经典：咔嗒检测用自回归（AR）模型的预测残差超阈值（Vaseghi & Rayner 1990；Godsill & Rayner《Digital Audio Restoration》1998）；简单 AR 残差阈值在比较中表现最好（CTU 2022 比较）【摘要 / 二手】。
   - 工程测试：OboeTester 用已知正弦预测样本值，偏差超容差即毛刺【读原文·文档】。
   - 我们：输出一阶差分对局部 20 ms MAD 的 k = 8 倍离群 + 「干净轨解释不了的部分 ≥ 一半」+ 输入里没有。思路上等于**用干净轨当预测器**（与 OboeTester 用已知正弦当预测器同类），比纯 AR 残差多了「排除原声自带瞬态」一层。**同类方法，没有统一标准参数**。
2. **参考信号**：干净轨（预测器）+ 带噪输入与背景轨（排除原有瞬态）。合理；业界检测器多为无参考（AR），我们有分轨所以能做得更准。
3. **过线口径**：0 个/分钟（012「A 档」）。业界没有通用阈值；修复领域按检出率 / 误报率曲线选阈值，不设「几个每分钟」【摘要】。
4. **汇总**：按段每分钟计数。单段 12 s，检出 1 个就是 5 个/分钟，0 线极敏感。
5. **统计**：
   - 计数服从近似泊松。要比较两个系统，按场景合并总分钟数，算率比的精确泊松置信区间【推断】。
   - 关键缺口不是样本量，是**检测器本身的准确率**：exp014 原声直通 0 / 0 / 60，参考降噪器与 GTCRN 59 / 0 / 1（`analysis.md` §2），cafe 上只有 14% 落在门控开关附近（`specs/rubric/scorecard.md:142`）。没有人耳标注就分不清真咔嗒与残留噪声起伏。
   - 估计所需人耳标注量【推断】：想把检测器精确率估到 ±10 个百分点（95%），需随机抽约 100 个检出点让人听；加 20–50 处人造咔嗒（不同幅度、落在人声 / 停顿上）量检出率。

**结论：可对齐**（与经典残差检测、OboeTester 同类）。维持「只报不判」直到：① 人造咔嗒检出率 ≥ 90%（建议值）；② 人耳标注精确率达标。
**与 012**：012 `verifiers.md:102` 已列「与人耳『咔』的一致率；人造插入咔嗒作对抗样本」为校准方法，一致；这次补的是所需标注量估算与业界参照。

## 9. 需要人拍板的点

本组只有 1 题需要人定，其余是纯技术题，AI 自己定。

**A-Q1：咔嗒检测（V-CLICK）要不要花你约 30 分钟听 100 个片段来校准？**
- 背景：现在检测器在降噪输出上几乎每段都报咔嗒，原声直通一段都不报。不知道是真咔嗒还是把残留噪声误当成咔嗒。
- 选项：
  - A：听。每个片段约 1 秒，你判「有咔嗒 / 没有」。100 段约 20–30 分钟。之后检测器可能转为正式判分。
  - B：不听。咔嗒一直「只报不判」，成绩单不靠它下结论。
- 代价：A 花你的时间；B 意味着降噪器若真有咔嗒，成绩单不会挡住它。
- 建议：A，但等 V-LAT 等确定性问题修完再听。
- **如果你不回，默认 B，后果是咔嗒问题只能靠你日常试用时偶然听到。**
