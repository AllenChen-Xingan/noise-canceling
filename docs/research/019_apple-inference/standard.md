## 0. 被评对象与基线

- **被评对象** = 一个（后端，模型，精度，配置）组合。例：（Core ML cpuOnly，GTCRN，fp32，缓存显式进出）。
- **必测模型**：GTCRN（主模型）· FastEnhancer-M（备选）。
- **基线**：ORT 1.31 CPU 单线程，配置同 `src/models/src/session.rs:30-45`。「更快 / 更好」都是对它说的。
- **同口径**（rustbe 与 applebe 已对齐）：输入 `resources/gtcrn/test_wavs/mix.wav`（16 kHz，610 帧，不够就循环）；1 帧冷启动 + 200 帧预热 + 6000 帧计时；单线程；3 轮交替跑；名额独占；记机型 · 系统 · 电源 · 跑前跑后负载。输出一行 JSON，字段以 rustbe 的 `bench/src/main.rs` 为准。
- **只认 Rust 调用测出的数**（D68）。Swift / Python 的数只作对照，见第 9 节。

## 2. 正确性：`BE-PARITY`

- **怎么测**：rustbe 的 `gtcrn-bench ort ... --dump-io <前缀>` 写出同一串输入和 ORT 输出（小端 f32，按帧拼接）。被评后端吃同一份输入，从零状态逐帧跑，缓存一路往下走。
- **算什么**：逐值最大绝对差 `parity_max_abs`、整段 SNR `parity_snr_db`、首个差 > 1e-3 的位置 `parity_first_bad`。算法同 rustbe 的 `parity`。
- **过线**：`parity_first_bad == None` 且 `parity_snr_db ≥ 60`。
- **60 dB 的依据**【推断】：rustbe 手写 Rust 对 ORT 是 134.0 dB，tract 130.4 dB，FE-M tract 110.8 dB（`notes/rustbe-numbers.md`）。fp32 不同实现之间差 100 dB 以上很常见。60 dB 相当于误差能量是信号的百万分之一，留了余量给「算子顺序不同的 fp32」，但会挡住 fp16（fp16 尾数只有 11 位，单次舍入误差约 −66 dB，累积后一般低于 60 dB【推断】）。
- **不拿 exp004 的 4.5e-7 当线**：那是 ORT 对 ORT（Rust 调与 Python 调同一个库），不是两个实现之间的差（怀疑派已指出，`notes/coreml.md` 文末）。
- **长时补充**：610 帧只有约 10 s。上用户电脑前还要在长音频（≥ 10 分钟，含长静音）上跑一遍，看缓存会不会漂、会不会出 NaN（DFN 有长静音出 NaN 的先例，`our-models.md` 第 3 行）。字段 `nonfinite_frames` 必须为 0。

## 3. 每帧耗时与尾部：`BE-FRAME` · `BE-FASTER`

- **怎么测**：只计「一次推理调用」（含输入写入和输出读出，不含 STFT）。计时器用 `mach_absolute_time` / `Instant`。
- **`BE-FRAME` 过线的依据**：延迟账里没有单列推理耗时。它被「跨进程环余量 3.00 ms」盖住，009 对这一项的定义是「盖住最坏推理耗时 + 唤醒抖动」（`docs/research/009_rust-ecosystem/decision.md:62`）。所以 max ≤ 2.0 ms 给唤醒抖动留 1 ms；p99.9 ≤ 1.0 ms 是今天 ORT 的水平（0.42–0.59 ms，r4）再放一倍【推断】。
- **`BE-FASTER` 的规则**：3 轮交替跑，各取 p50 和 p99.9。只有「本后端最慢一轮」比「ORT 最快一轮」还快，才写「更快」，并写倍数（ORT p50 中值 ÷ 本后端 p50 中值）。轮间范围有重叠就写「持平」。
- **FE-M 的预算**是每 10 ms 一帧，同一条线也适用（线是绝对毫秒，不是占预算比例）。
- **`BE-DEADLINE`**：6000 帧只有约 96 s，看不到罕见的长尾。按实时节奏（`pace_ms`）跑 10 分钟（GTCRN 37 500 帧），数**迟到**超过 3.0 ms 的帧：迟到 = 一帧做完的时刻 − 该到的时刻，把唤醒迟到也算进去（codex 第 1 轮 #2：只数推理调用耗时，醒晚了几毫秒也会报 0）。3.0 ms 就是延迟账里那 3 ms 余量，它本来就要盖住「最坏推理耗时 + 唤醒抖动」。过线是 0 帧。早期 build（2026-11-02 19:00 前）只有 `frames_over_3ms`（调用耗时），不能用来判这一条。

## 4. 实时线程安全：`BE-RT-ALLOC` · `BE-RT-SAN` · `BE-RT-XPROC`

这三条决定后端的**接法**：三条都过 → 可以在推理线程每帧直接调；有不过的 → 像今天的 ORT 一样登记豁免，或者挪到别的线程，再看 `BE-FRAME` 的尾部。

- **`BE-RT-ALLOC`**：用 libmalloc 的 `malloc_logger` 钩子数全进程分配（`apple/alloc_hook.c`，Instruments 用的同一个钩子）。只数计时段。**判 0 用整数** `process_allocs_total == 0`，而且必须是开了计数钩子（`--count-malloc`）的那一次；`process_allocs_per_frame` 只保留三位小数，6000 帧里 1 次分配会显示 0.000，不能用来判；字段为 null（没开钩子）一律不算过（codex 第 2 轮 #7）。注意：
  - 这个数和 rustbe 的 `rust_allocs_per_frame`（只数 Rust 分配器）不是同一个量，两个名字不混用。
  - 别的进程（神经引擎守护进程 `aned` 等）里的分配看不到，所以要和 `BE-RT-XPROC` 一起看。
  - 规约 B 档只要求「我们的 Rust 代码零分配」，ORT 内部分配允许登记（`specs/rust/architecture.md` §4）。对第三方后端也要求 0，是为了区分「能直接调」和「只能登记」【AI 定；人可改】。
- **`BE-RT-SAN`**：Clang RealtimeSanitizer，B 档用法照规约 §5.5（`halt_on_error=false`、必须符号化、去重后的唯一栈对豁免表）。每个新后端要建自己的豁免表（命名空间不同：Core ML 是 Objective-C 方法名，BNNS 是 `BNNS*`，MLX 是 `mlx::`）【推断】。RTSan 拦不到不经 libc 的自旋和缺页（`notes/bnns-graph.md`），所以它过了也不等于没锁。
- **`BE-RT-XPROC`**：推理线程每帧发出的 mach 消息数必须为 0。要 sudo（`dtruss -t mach_msg` 或 `fs_usage`），命令写成文件交人跑。不能跑 sudo 时，用两条旁证：`MLComputePlan` 显示所有算子都在 CPU（Core ML / BNNS 才有）；`powermetrics` 里神经引擎和 GPU 功率在跑与不跑时没有差别。

## 5. 冷启动：`BE-COLD`

- **怎么测**：`compile_ms`（mlpackage → mlmodelc 或 mlmodelc → BNNS 图，一次性准备，单列）· `open_ms`（加载，**不含** `compile_ms`）· 200 帧预热的总时长 · 预热后第 1 帧耗时。判 `BE-COLD` 时用 `compile_ms + open_ms + 预热`（首次启动）和 `open_ms + 预热`（已有缓存）两个数。
- **为什么要看**：换模型时，新 Pipeline 在非实时线程建好、预热后再送进实时线程（规约 §3.5），所以冷启动不进实时线程，但决定「用户换模式后多久生效」和「开机多久能用」。500 ms 按「人按下开关后半秒内生效」定【AI 定；人可改】。
- 神经引擎有「空闲约 5 s 后第一帧约 260 ms」的他人实测（`notes/realtime-and-bindings.md`），所以对用神经引擎的组合，还要测「停 10 s 再来一帧」的耗时。

## 6. CPU 与耗电：`BE-CPU` · `BE-POWER`

- **`BE-CPU`**：按实时节奏跑（`pace_ms` = 16 或 10）60 s，`cpu_over_wall` = 计时窗内的进程 CPU 时间 ÷ 墙钟时间（窗一结束就读，对拍等后处理不算进去；codex 第 1 轮 #4，19:00 前的 build 含对拍，略偏高），单位是「核」，和活动监视器同一个算法（100% = 一个核）。总线来自 D69（人原话「计入，如果别人都是2-5%，我们必须很低，我的底线是1%」，补一句「或者说最高2%」）：整个降噪软件常开时总占用**目标 ≤ 0.01 核、硬上限 ≤ 0.02 核**，含采集 · STFT · 降噪模型 · 认人 · 场景 · 修音 · 输出。D75 之后 CPU% 只作参考、不挡；作参照时降噪推理按两档各分一半（≤ 0.010 核 / ≤ 0.005 核）。分摊见 §6.1。**注意要用实时节奏的数**：连续跑的数会低估约 5–7 倍（帧间降频）。
- **测量条件要写明**：计时线程设 QoS `user-interactive`（同 rustbe），系统多半把它放在性能核上。能效核上同样的活更慢，占用百分比会更高；活动监视器不按核类型折算。所以每个 `BE-CPU` 数都要标「性能核」，能效核另测（未量化）。

- 降噪模型分一半：它是唯一必须每帧都跑的大件；参照里 RNNoise 约 1.7% 个核、PercepNet < 5%（§8）。
- 认人只分 0.15%（上限 0.30%）：它不在声音通路上，可以降频（例如只在 VAD 判有人声时跑、判断间隔从 0.5 s 拉长）或换更小的声纹模型。这是 019 实体之外的事（认人归 exp005 / 013 线）。
- VAD、场景按现状给。

**风险（已转交大总管）**：
1. **认人判断回路 ≈ 1.2% 核：超上限 4 倍，单项就超整机目标。** 要降到 0.30%（上限）约 4 倍、到 0.15%（目标）约 8 倍。不属于推理后端这件事。
2. **降噪模型：最快的手写 Rust GTCRN（0.63%）不超上限分摊（1.00%），但超目标分摊（0.50%）1.25 倍。** ORT（2.3%）超上限。019 基准直接看：要进目标，每帧平均 ≤ 0.08 ms。
3. **FE-M 在 ORT 上 ≈ 3.7%：超上限 3.7 倍**，要快约 3.7 倍才进上限、7.4 倍才进目标；D33 的「同接口备选」可能要按这条重估。
4. STFT、重采样、采集输出、修音四项还没测过（目标合计 0.17%，上限 0.34%）。
- **注意**：神经引擎和 GPU 的工作不算进 `cpu_over_wall`，所以凡是用到它们的组合，必须看 `BE-POWER`。
- **`BE-POWER`**：`powermetrics -i 500 --samplers cpu_power,gpu_power,ane_power`，先空闲 30 s 取基线，再按实时节奏跑 60 s，报 CPU / GPU / 神经引擎三项功率的增量（mW）。**判的是每帧耗电**：µJ / 帧 = (三项增量之和，mW) × 时长 (s) ÷ 帧数 × 1000。理由（D70，人原话「必须我们有办法完全榨干硬件的性能，以及非常低能耗」）：快而费电不算赢——GPU / 神经引擎可能每帧更快，但唤醒它们的固定功耗可能更高，只有每帧耗电能把两者放在同一把尺子上。要 sudo，由人跑：rustbe 的 `tools/power_run.sh`、applebe 的 `apple/power.sh`，两者口径要一致（合并前对一次）。

### 6.2 选赢家的规则【AI 定，依据 D70；人可改】

1. 先过挡线（= 总表里「挡上用户电脑」「挡合并」「挡默认后端」的全部）：`BE-PARITY` · `BE-FRAME` · `BE-DEADLINE` · `BE-IMPACT`（≤ 2%）· `BE-COLD` · `BE-POWER` 的「不高于 ORT」（要同场 ORT 基线）· `BE-SIZE` · `BE-MEM` · `BE-OS` · `BE-RT-SAN` · `BE-RT-ALLOC`（= 0，大总管 2026-11-02 定）。不过的不进排名。**有挡线还没测的，只能「暂排」，方案里写明缺哪几条。**
2. 过线的按**每帧耗电**从低到高排。
3. 每帧耗电相差不到 10%、**或差值小于噪声底（多轮空闲基线的离散）** 的算并列，再按 `BE-IMPACT`（越低越好）、再按 p99.9（越低越好）排。
4. 还没有耗电数字（人还没跑 sudo）时，只能按 `BE-IMPACT` 暂排，再不行按 `cpu_over_wall`，并在方案里写「暂排，待耗电数」。

### 6.3 `BE-IMPACT`：对性能的影响（D75）

- **前台负载**：`apple-rs` 的 `loadgen`，开满全部逻辑核，每核对自己的 4 MB 数组做 400 遍乘加（`mul_add`），工作量固定，只看墙钟。选它而不是 `cargo build` 的理由【AI 定；人可改】：① 可重复——不读写磁盘、不联网、不受增量编译缓存影响；② 同时压算力和缓存 / 内存带宽，降噪线程抢核、抢缓存都会让它变慢；③ 开满所有核，是用户「电脑正忙」时最容易感到卡的情形。
- **做法**：「关 / 开」交替 7 对（`apple-rs/tools/impact.sh`）。「开」= 降噪组合按 16 ms 节奏在后台跑，线程设置用 D74 默认（time-constraint 开、不加工作组）。
- **算**：慢了多少 = 开的中位 ÷ 关的中位 − 1。同时报 7 次「关」之间的离散度，当量测噪声底：噪声底如果大于 1%，结论只能写「≤ 噪声底」。
- **过线**：≤ 1% 目标、≤ 2% 挡线。维度【已定 · D75】，两个数沿用 D69 的两档【AI 理解，待人确认】。
- **第一次实测（2026-11-02）——⚠️ 作废**：`impact.sh` 旧版留下 21 个孤儿降噪进程一直在跑（后台 `eval … &` 只杀了子 shell），「关」组其实也开着降噪，下面的数不能用，脚本已修。原记录照留：`loadgen` 开满 10 个逻辑核、每次约 5.5–8 s，「关 / 开」7 对。BNNS rt：慢 5.9%，但 7 次「关」之间离散 10.6%；手写 rt：−0.6%，离散 22%（`apple/results/20261102-182000-impact-bnns/`、`…-182200-impact-native/`）。信号淹在噪声里，只能写「≤ 噪声底」。原因推断：前台负载占满全部核（含能效核），调度本身的抖动就有 10–20%。**测法要改**：前台负载用「性能核个数」个线程、每对交替 15 次以上、用最小值而不是中位（最小值最接近无干扰时的真实时长）；改完再测。

## 7. 体积、系统、换模型、微调：`BE-SIZE` · `BE-OS` · `BE-SWAP` · `BE-TRAIN`

- **`BE-SIZE`**：数安装包里因这个后端多出的字节（动态库 / 静态链接增量 + 模型文件）。系统自带框架（Core ML、Accelerate）记 0。ORT 静态链接的增量要实测（`cargo bloat` 或对比带 / 不带 ort 的二进制大小）；如果 ORT 本身就超 5 MB，这条会让 ORT 方案不过，这是有意的（D70「轻量」）。
- **`BE-MEM`**：`apple-rs` 用 `proc_pid_rusage(RUSAGE_INFO_V4).ri_phys_footprint` 读三次：加载前、预热后、跑完；字段 `footprint_before_mb` / `footprint_warm_mb` / `footprint_end_mb`。判的是「预热后 − 加载前」。跑完比预热后还涨，说明每帧在泄漏或攒缓存，单列报出。rustbe 的程序已加同名三个字段（MB = 1024²；「加载前」在输入帧备好之后读，所以输入数据本身约 12.7 MB 不进差值）。

## 8. 参照：成熟产品与开源实时实现怎么守这些线

> 详细出处与等级见 `notes/references-products.md`（子代理写，已自审）。下面三条都是别人的数字，不是本机实测。

- **平均耗时**：能常开的 ML 降噪，公开数字都在一个核的 2–5%。PercepNet 不到 5%【官方】；RNNoise 2017 版约 60 倍实时，折合约 1.7% 个核【推断，按其公开倍数换算】。这是参照：人据此定了更严的整机 ≤ 1%（D69），见 §6.1。
- **尾部**：没有一家公开 p99.9 或最坏一帧。公开的线只有 NVIDIA「p95 小于一帧」【官方】和 DNS 挑战赛「每帧处理时间小于步长」【官方】，都比我们的 `BE-FRAME` 松 5–8 倍。产品跟不上时都是降级：DFN 插件自动加一帧延迟【源码】、Discord 关掉降噪、Teams 退到低档。所以尾部线只能从我们自己的延迟账定（§3），并加了 `BE-DEADLINE`。
- **实时做法**：手写实现（RNNoise、SpeexDSP、RTNeural、苹果示例）都是创建时分配、每帧不分配【源码 / 官方】；用 tract 的 libDF 每帧都分配【源码】，和 rustbe 实测 tract 每帧 2247 次一致。NVIDIA 走 GPU，每帧中位数 0.37 ms，却要独显、约 215 MiB 显存、8.8 s 冷启动【官方】，是 `BE-COLD` 和 `BE-SIZE` 的反例。
- **查不到的**：苹果语音突显（Voice Isolation）的实现完全没公开；Krisp 的数字（约 15 ms 延迟、3–5% 个核）只见搜索摘要，原件未亲读，不引用。
