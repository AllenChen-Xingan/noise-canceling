# 取舍卡 · 实时语音降噪与「声音自然」的前沿全景：哪些能被我们用上

> 2026-10-30 · 手下 sota 起草。依据：`sources.md`（逐条出处）· `gap.md`（技术 × 阶段）。全程只读调研：**没有训练、没有推理、没有下载权重**。12 个检索 / 怀疑代理 + 1 个完整性批评者 + 2 个补充块（⑦ 延迟可感、⑧ 补偿与 RX），每块都被怀疑派回原文反驳过一轮，本卡用的是改正后的说法。
> 排序遵照人 2026-10-30 的新要求：**训练放最后；先用现成模型 + 工程手段；延迟必须发现不了；能耗要低。**
> ⚠️ 「需要你拍板的地方」AI 只列选项与建议，**不代填**。

## 一句话

**世界上没有一个「现成、实时、开源、又比 DPDFNet 明显更好」的降噪模型；真正能用上的新东西是三样：一个 32 ms、MIT 许可的新模型 FastEnhancer（可能让延迟降到 GTCRN 一档而效果更好），一套不用训练的工程手段（可调的「背景保留」旋钮、因果带宽扩展、响度与音色均衡），以及几个只能我们自己量的实验（延迟能不能被察觉、开着降噪多耗电）。** 生成式「修复」（Adobe 那一类）会改字，和吃字一样危险，不进实时链路。

## 你问的几件事，直接回答

| 你问的 | 答案（详见 gap / sources） |
|---|---|
| 有没有人做过 RX 那样的降噪 | **RX 公开的只有交互和功能说明**：Dialogue Isolate 把声音拆成「人声 / 混响 / 噪声」三路各配一个增益旋钮；Voice De-noise 是 64 个心理声学频带的零延迟自适应门限；Spectral Recovery 合成截止频率以上的高频（RX 12 官方文档）。没有论文、专利。**开源界没有任何人和 RX 做过公开对比** |
| RX 是不是最好的 | **离线后期里它很强，但不是公认第一**：Production Expert 2025 八款对比，RX 四局一局没赢；2024 读者投票（选项随机排序）RX 6 款里第 3（dxRevive、Hush 在前）——都【传】，都是**离线 Best 模式**。实时版：RX 11 约 2048 采样（≈43 ms），RX 12 有用户测得 85 ms（单一来源），超我们 75 ms 门槛。**能学的是交互层**：「分轨 + 混回」的旋钮 |
| 这些公司做不做「降噪后补偿」 | 做，分两类：①**修原波形**——带宽扩展（RX Spectral Recovery、Opus 1.6 BWE）、音色均衡、残噪地板；②**生成式重建**——Adobe Enhance、NVIDIA Studio Voice（低延迟版 ≤110 ms、要 GPU）。②会改字：URGENT 2025 纯生成式系统**中文 CAcc 只有 20.1%**，而 DNSMOS 照样给高分；Adobe 在混响下 dWER 18.87%（StuPASE 论文）。**我们只做①** |
| 认人声有没有新东西 | 2025–26 新的很少：VoxLock 仍是唯一能下手的（005 结论不变）。新思路是「**无注册**的前景说话人检测」（谁持续在场谁是主人，不是谁最响），正好补 005 第 1 步门控「开头别人先说话」的坑，但没代码，要训练 |
| 耗电 | **公开世界里没有任何降噪产品在 Mac 上的耗电实测**。Neural Engine 不适合逐帧小模型（DPDFNet 的 Core ML 版每帧 3.69 ms，比 CPU 版 0.89–1.40 ms 还慢），继续 CPU。只能自己量 |
| 榜单 | VoiceBank 已饱和；DNS 2023 后停办（测试集还能用）；URGENT 冠军都是 1 亿参数级、非因果，名次对我们没用；最贴我们的是 CHiME-9 ECHI（真实 babble、强制因果）。**真实录音上 DNSMOS 和真人分对不上**，验收靠吃字率 + UTMOS/SCOREQ + 人耳 |
| 别的行业怎么让人感觉不到延迟 | 关键是分清谁在听：**说话人自听** 3–10 ms 就能察觉（助听器）——我们不让说话人监听，就不碰这条；**对方听**普通对话几百 ms 才察觉，但**快速轮流说话时受训者往返 90 ms 就察觉**；**有视频时**声音比画面晚 125 ms 可察觉，我们的延迟会原样叠到会议软件已有的偏差上。**没有任何实验测过「再加 45 / 75 ms 会议里能不能察觉」——只能我们自己测** |

## 这次不可妥协的几条（AI 起草，**人还没定**，见 `must-know.md`）

1. 因果实时：端到端 ≤ 75 ms 入围，单线程每 10 ms ≤ 2 ms
2. 许可证与 GPL-3.0 兼容（代码、权重、训练数据）；「没代码没权重」单列为「需自己实现」
3. 能在 Rust 里逐帧跑

## 我放弃什么

- **生成式修复进实时链路**（Adobe Enhance、Studio Voice、流式扩散 / 流匹配）：会改字，且 Mac CPU 跑不动
- **Neural Engine / Core ML 逐帧推理**：现有证据都显示对 10 ms 小帧更慢、更抖（推翻设计稿 §11「ANE 主要用来省电」的预期，要省电先从「少算」入手）
- **2026 年新出的一批轻模型**（CoFi-Lite、HALO、LaCo-SENet、AdaptCRN、µNet、RT-SEMamba）：几乎都卡在「无 LICENSE / 无权重 / 专利」
- **排行榜名次**：URGENT、VoiceBank、聚合榜对「因果 + 小模型」没有参考价值
- **Opus LACE / NoLACE**：要编解码器内部参数，降噪后用不了

## 让哪把尺子变好（`.42cog/intent.md`）

- **清楚**：#3（背景保留旋钮、送原声）直接对冲吃字；#5 的规则防「改字」。#1 在 babble 下是否更好**没有证据**，要 exp003 判
- **自然**：#5 补高频与音色；#3 防「真空感」；生成式被拒是因为它「好听但改字」
- **轻快**：#1 可能把延迟降约 30 ms；#2 回答「延迟能不能被察觉」；#4 回答「多耗电」——三件都是现在完全没有数字的
- **最大的反向风险**：FastEnhancer 的分数全部来自合成集平均分，**低 SNR 和 babble 下可能不如 DPDFNet**；若 exp003 听测如此，就回到 D01 的原题

## 失败条件（出现就换）

| 对象 | 失败条件 | 换成 |
|---|---|---|
| FastEnhancer | M5 含 STFT 最坏一帧 > 2 ms；或 AB 听测在咖啡馆片段明显不如 DPDFNet-2；或吃字率高于原声直通 | 回到 DPDFNet-2 / GTCRN 二选一（D01 原题） |
| 延迟实验 | 盲测里 +45 ms 也能被稳定察觉 | 延迟上限收紧到 GTCRN / FastEnhancer 档，DPDFNet 只作离线参照；考虑「停顿处切换」方案（gap 4） |
| 后端 | ort 在负载下 p99.9 超 2 ms 或出 xrun | 换 Accelerate 自写推理（altvane 路线）或 BNNSGraph（macOS 15+） |
| BWE | 开启后吃字率上升，或说话人相似度下降，或 AB 不偏好 | 关掉 BWE，只留 LTASS 均衡 |

## 与已有调研的关系

- **002**：结论不变；DPDFNet 60 ms 被三方印证；补「训练数据含 FSD50K（有 NC 片段）」进 NOTICE 登记（D14 已要求写明训练数据情况）
- **004**：加强「不只看 DNSMOS」；建议补 DNS5 盲测集与 Apple Voice Isolation 对照录音
- **005**：结论不变；**请转 pse 线**：①arXiv 2610.35272 的开源因果主讲人隔离器（Krisp 基准 WER 5.74% vs Krisp 5.63%，权重许可 `other`）；②无注册前景说话人 VAD（FVAD 2609.19856、EEND-SAA 2509.11957）可补门控「开头别人先说话」；③REAL-TSE 冠军 CARTSE 训练里最大化 DNSMOS，借配方时剔掉

## 仍未补齐的缺口（必须实测才能定，已在上面 #1、#2、#4 里）

- FastEnhancer 在 babble / 低 SNR 下的表现、M5 含 STFT 的真实每帧耗时
- 「再加 45 / 75 ms」在会议里能否察觉；会议软件自身的音画偏差
- 降噪开一小时的耗电；ort vs Accelerate 在负载下的 p99.9
- Opus BWE 权重的许可文本；BNNSGraph 是否支持 GRU
