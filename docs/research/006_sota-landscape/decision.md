## 一句话

1. **RX 在离线后期里确实很强，但不是公认第一，它的实时版太慢，我们用不上；能学的是它「人声、背景各一个旋钮」的做法。**
2. **降噪后的补偿能做，但只补高频和音色；会「重新生成声音」的那类修复（Adobe 那种）会改字，和吃字一样危险，不用。**
3. **延迟能不能被察觉、开着降噪多耗电，全世界都没有现成数字，只能我们自己测；另外有一个新的现成模型（FastEnhancer）在合成数据上比 GTCRN 好、延迟和它一样短，值得放进这次的听测。**

## 你问的几件事，直接回答

| 你问的 | 答案 |
|---|---|
| **RX 是不是最好的** | **你的感觉在离线后期上没错**，RX 是最全、最好用的修复工具箱。但在几次多家对比里它不是第一：媒体组织的 2024 读者投票（选项随机排序）RX 6 款排第 3，2025 年 8 款对比 4 个例子 RX 一个都没拿第一（Hush、dxRevive、Supertone 各有胜场）——这些都是媒体自办、算传言，而且**比的都是 RX 的离线最好档**。**实时版**：RX 11 约 43 ms，RX 12 有用户测到 85 ms（单一来源），超出我们 75 ms 的入围线 |
| **有没有人做过 RX 那样的** | RX 只公开了功能说明，没有论文：Dialogue Isolate 把声音拆成「人声 / 混响 / 噪声」三路、各配一个增益旋钮；Voice De-noise 是 64 个按人耳划分的频带、零延迟自动门限；Spectral Recovery 在截止频率以上合成高频。**没有任何开源项目和 RX 做过公开对比** |
| **这些公司做不做「降噪后补偿」** | 做，两类：①**修原来的声音**——补高频（RX Spectral Recovery、Opus 1.6 的带宽扩展）、调音色、留一点背景；②**重新生成声音**——Adobe Enhance、NVIDIA Studio Voice（低延迟版也要 ≤110 ms 且要 NVIDIA 显卡）。②会改字：URGENT 2025 比赛里纯生成式系统**中文内容词只对了 20.1%**，而常用的自动打分照样给高分；Adobe 在有混响的录音上错词率 18.87%（StuPASE 论文）。**我们只做①** |
| **别的行业怎么让人感觉不到延迟** | 先分清谁在听：**说话人听自己**，3–10 ms 就能察觉（助听器）；**对方听**，普通聊天几百 ms 才察觉，但快速轮流说话时受过训练的人往返 90 ms 就能察觉；**有视频时**声音比画面晚 125 ms 可察觉。行业做法三条：①**不让说话人听处理后的自己**（我们设计稿已定）；②**把延迟算进整条链的预算**（广播、VoIP 都这样，降噪模块一般只分到 15–25 ms，如 Krisp）；③**只在停顿处改变延迟**（网络电话的抖动缓冲就是这样悄悄变的，人听不出）。**当前判断**：多 45 ms 在普通对话里大概率察觉不到；快速抢话和视频嘴型有风险——**没有任何实验测过「再加 45 / 75 ms 开会时能不能察觉」，要我们自己测**（下面第 2 件事） |
| **耗电** | **没有任何降噪产品公开过 Mac 上的耗电数字**。你定的上限是「约一个 CPU 核的 1/5」（D31）。就算力而言，现成模型都远低于这条线（每 10 ms 算 0.2–1.4 ms）；真正的耗电要用系统工具实测。Apple 的神经网络芯片（Neural Engine）目前**没有证据**能让这类小模型更省电（唯一的公开移植反而每帧更慢，但机型不同、没测功耗），先用 CPU |
| **认人声有没有新东西** | 很少。VoxLock 仍是唯一能下手的开源模型（005 结论不变）。新思路是「**不用注册**、谁持续在说话谁是主人」的检测，正好补 005「会议开头别人先说话会认错人」的坑，但没代码、要训练 |
| **榜单** | 老榜（VoiceBank）已刷满；微软 DNS 比赛 2023 年后停了（测试集还能用）；URGENT 冠军都是上亿参数、不能实时的模型，名次对我们没用；最贴近我们的是 CHiME-9（真实餐桌多人说话、要求实时）。**真实录音上，自动打分和真人感受对不上**，所以我们验收靠吃字率 + 人耳 AB |
| **训练** | 按 D29 放最后。下面 5 件事都**不用训练** |

## 这次不可妥协的几条（AI 起草，**人还没定**，见 `must-know.md`）

1. 因果实时：端到端 ≤ 75 ms 入围（最终上限按 D30「发现不了」由实验定）；每跳计算 ≤ 跳长的 20%（10 ms 跳即 ≤ 2 ms）
2. 许可证与 GPL-3.0 兼容（代码、权重、训练数据）；「没代码没权重」单列为「需自己实现」
3. 能在 Rust 里逐帧跑

## 我放弃什么

- **生成式修复进实时链路**（Adobe Enhance、Studio Voice、流式扩散）：会改字，且 Mac CPU 跑不动
- **现在就上 Neural Engine**：没有证据更快或更省电；进第 4 件事当一档实测，不当默认
- **2026 年新出的一批轻模型**（CoFi-Lite、HALO、AdaptCRN、µNet、RT-SEMamba）：几乎都卡在无许可 / 无权重 / 专利；LaCo-SENet 权重 MIT 但代码无许可、逐帧太慢
- **FastEnhancer 48 kHz 版**（算法延迟约 21 ms、全频带，本来很诱人）：训练数据含标明「禁止出境」的韩语语料，过不了许可命门；只用 16 kHz DNS 版
- **排行榜名次**、**Opus LACE / NoLACE**（要编解码器内部参数，降噪后用不了）

## 让哪把尺子变好（`.42cog/intent.md`）

- **清楚**：#3 直接对冲吃字；#5 的规则防改字；#1 在嘈杂人声下是否更好**没有证据**
- **自然**：#5 补高频与音色；#3 防「真空感」
- **轻快**：#1 可能把算法延迟降约 28 ms（端到端少得略少，要实测）；#2 回答「能不能察觉」；#4 回答「多耗电」——三件现在都没有数字
- **最大的反向风险**：FastEnhancer 的分数全来自合成数据平均分，咖啡馆场景可能不如 DPDFNet

## 失败条件（出现就换）

| 对象 | 失败条件 | 换成 |
|---|---|---|
| FastEnhancer | exp003 吃字率高于原声直通 +1 个百分点（D10 口径）；或你的 AB 在咖啡馆片段偏好 DPDFNet-2；或 M0 实测端到端 > 45 ms | 回到 DPDFNet-2 / GTCRN 二选一（D01 原题） |
| 延迟实验 | +45 ms 在 20 次强迫选择里 ≥ 15 次被选对 | 上限收紧到 32 ms 档模型；DPDFNet 只作离线参照 |
| 推理方式 | `ort` 在压力脚本下一小时内出现一次超时（每跳计算 > 跳长 50%）| 先换小一号模型或 GTCRN；再考虑 BNNSGraph（要 macOS 15+，我们下限 14.2，要留 ort 兜底） |
| 耗电 | 降噪进程平均超过 D31 的约 1/5 核 | 加大音频缓冲（多几毫秒延迟）或换小一号模型 |
| 带宽扩展 | 开启后吃字率上升或说话人相似度下降，或你 AB 不偏好 | 关掉，只留均衡与响度 |

## 小词表

| 词 | 意思 |
|---|---|
| 算法延迟 / 端到端延迟 | 模型本身要攒多少声音才能出结果 / 从麦克风到对方会议软件的全部附加延迟 |
| 每跳 | 模型每次处理的一小段（10 ms 或 16 ms） |
| 吃字率 | 处理后语音识别比原声少认出的字的比例（D28 用 Qwen3-ASR） |
| 带宽扩展 | 把只有低频的声音（如蓝牙麦）补出高频，听起来更亮 |
| 生成式修复 | 不修原声，而是让模型「重新说一遍」；好听但可能说错字 |
| babble | 背景里很多人同时说话的嘈杂声（咖啡馆） |
| ONNX / ort | 通用的模型文件格式 / 我们在 Rust 里跑它的库 |
| Neural Engine | Apple 芯片里专跑神经网络的单元 |
