# telegram 项目的 AI 自主系统：调研汇总

整理于 2026-10-29。4 个 agent 只读调研 `telegram accessibility `（末尾带空格），从四个角度看：方向层、派活机制、护栏与验证、实际运转。目的是给降噪项目搭同类系统时参考。

---

## 一、它是什么

由 `aias-meta-init` 生成：AI 在人少量介入下自己推进一个 Rust 项目。
4 天（10-23 → 10-26）的产出：19 个提交、18 个 PR 全部合并、约 2.4 万行自研 Rust、47 个 issue（几乎都是 AI 开的）、约 30 个手下会话。

四个部分：

| 部分 | 落在哪 | 作用 |
|---|---|---|
| 方向层 | `.42cog/`（陈述句）· `CLAUDE.md`（祈使句）· `specs/`（标准） | 告诉 AI 做什么、什么算好 |
| 派活层 | 大总管 + tmux 手下 · `state/coord.md` · `state/handoff/` · `_tmp/<批次>/` | 多条线并行，上下文断了能接上 |
| 护栏层 | `guard-git.sh` hook · GitHub 规则 · CI · 专用检查脚本 · 自审 + codex 评审 | 拦住 AI 犯错，自动判对错 |
| 拍板层 | 「待人拍板」题面 · `docs/plan/NNN_decisions-*` · 「人定 YYYY-MM-DD」规则 | 人只答选择题，答案回写原文件 |

## 二、最值得学的 6 点

1. **一句方向 + 三把尺子。** `.42cog/intent.md:9`「快、AI 友好、无障碍友好」，每个词拆成一把可量的尺子，硬规则是「至少一把变好，另两把不变差」。这三把尺子后来一路传到 issue 标签、PR 模板和看板。整套系统里这一处最有价值。
2. **意向书的四个配套段落**：真难题（还写了哪些不算）· 不做什么（每条附理由）· 真相源权重（第 1 级是「我本人的实际体验」）· 合格判据分机器 / AI / 人三层。
3. **规约用「夹具 → 正例 → 反例 + 错在哪」的格式**（`specs/style/message.md`）。正例直接当快照测试的期望值，AI 拿来就能改代码、写测试。注意：这些是项目跑起来以后长出来的，骨架自带的模板反而空着。
4. **拍板批处理。** 只有大总管跟人说话。要人定的事攒成选择题，一次问完（如 V1–V23 共 23 题一次答完），答案回写进规约并标「人定」。人只在少数节点出手，几天就推进了 9 块。
5. **先做有界实验和人工实测，再写代码。** exp002 测出 TDLib 耗时不到 1%；人试听后推翻了「方向键」方案，也发现礼貌式播报会打断朗读。这些都在写代码之前发现。
6. **踩一次坑就固化成脚本或规则。** 比如 `check-no-debug.sh` 防止隐私泄露（带自测）；`state/memory/` 里的三条教训：路径末尾空格、唯一写入口、检查脚本静默失败。

## 三、最浪费的 5 点

1. **评审轮数失控。** codex 评审 005 跑了 13 轮、006 跑了 11 轮，约 290 万 token，几天就把额度烧完。后几轮大多在挑扫描脚本自己的漏洞，回报递减。
2. **状态写在四处**：coord（332 行）、board、handoff（34 份）、status，同一件事抄两三遍。大总管的 token 大多花在记账上。
3. **有些规则没人执行。** `changelog.md` 写完开仓那条就再没更新；`meta.md`、`vault/truth/`、`specs/style/positive.md` 等是空架子；「技能内置判据」写了，四个技能其实都没建。
4. **`_tmp` 有 181 MB**，大头是克隆来的先例仓库（168 MB）和 codex 日志，收尾时没清理。
5. **护栏能被 AI 自己绕过**：`ATG_CONFIRMED=1` 前缀是 AI 自己加的，hook 无法确认人真的同意过。另外，「速度很快」这把尺子从头到尾没有基准测试。

## 四、坑 → 规则（可直接借鉴）

| 坑 | 长出的规则 |
|---|---|
| 隐私泄露口逐个补，越补越多 | 唯一写入口 + 穷举测试 + 变异检验 |
| 检查脚本里的 `\|\| true` 吞掉报错，照样打 ✓ | 守门脚本必须带自测，并在故意埋了违规的副本上实扫 |
| 路径末尾空格让链接参数被拆开 | 路径全加引号；第三方构建从不带空格的软链路径编 |
| 手下报到后就停住，空等 1.5 小时 | 交代里写明「报到后不要停，直接接着干」 |
| 弹窗测试抢前台、打扰人 | 每次不超过 1 分钟可以随时跑，更长的先问人 |
| 评审停不下来 | 停止线：P0/P1 清零，且连续两轮没有 P0/P1；剩下的 P2 开 issue |

## 五、搬到降噪项目：照搬 / 简化 / 新增

**照搬**
- intent 的结构：一句方向 + 三把尺子 + 真难题 + 不做什么 + 真相源权重 + 三层判据
- 陈述句 / 祈使句 / 标准三层分开；方向只留一份正本，别处只放指针
- 拍板批处理，答案回写原文件，带日期和决策编号
- issue → 分支 → PR → 人合并；`guard-git.sh`、GitHub 规则、CI 骨架、issue/PR 模板
- 交代和首条消息先写成文件；手下不碰 git；全机一个重活名额
- `state/memory/` 的「为什么 / 怎么用」写法

**简化**
- 状态只留两处：`board.md`（现状 + Top 3）和 `handoff/`；coord 只记手下表和名额；changelog 要么真写，要么删掉
- 删掉或推迟：`meta.md`（并进 README）、`vault/`、`notes/`、style 模板，等有内容再建
- 线少时用会话内子代理；tmux 手下只留给半小时以上的长线
- codex 评审设轮数上限（3–5 轮），P2 一律转成 issue
- `common.md` 做成项目级常驻文件，不要每批复制；克隆的仓库和评审日志收尾就清

**新增（音频专用，telegram 没有）**
- **实时安全检查**：音频回调里不分配内存、不加锁、不做 IO。用 `assert_no_alloc` 加一个扫描脚本，作用相当于 `check-no-debug.sh`
- **延迟与性能基准进 CI**：每帧耗时看 p99.9 和最大值，和基线比，超过阈值就判失败
- **音质回归门禁**：固定的含噪测试集 → 吃字率（Whisper）、DNSMOS / NISQA、LTASS 偏差，和入库的基线比。作用相当于 telegram 的快照测试
- **音频设备名额**：替代「弹窗 / 抢前台」那条，占麦克风或扬声器的测试要排队
- **听感验收清单**：人做 AB 对比，只听机器挑出来的 10 段（对应设计文档 §13 的飞轮）
- 自审视角按领域定：DSP 工程师 · 实时系统工程师 · 开会的用户（含 VoiceOver 用户）
