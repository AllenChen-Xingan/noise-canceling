## 我要作的决定

本项目的 Rust workspace 拆成哪些 crate、核心 trait 长什么样、实时安全规则用什么工具机器检查，以及人提的「用 AST（抽象语法树）做模块化」在哪里用、用到什么程度。

## 一、不可妥协的

| # | 不可妥协的 | 为什么它是命门 | 怎么算满足 |
|---|---|---|---|
| 1 | **离线评测与实时用同一份处理代码**：处理核心不依赖任何平台、IO、线程 | `.42cog/intent.md` 作品区、`.42cog/cog.md` 关键关系；一旦两份代码，评测分数就不再预测线上听感（真难题 2） | 核心 crate 的依赖树里没有 cpal / objc2 / CoreAudio；`eval` 与实时进程调用同一个 `process` 入口；有机器检查（依赖方向规则）挡住反向依赖 |
| 2 | **实时路径不分配、不加锁、不阻塞、不 panic，而且由机器证明** | 设计稿 §7「实时编程纪律」；一帧超时 = 一次爆音（§11），出事必须送原声（D03） | 每条规则至少一种机器检查（运行时检测或静态 lint），进 CI；人肉代码审查不算 |
| 3 | **模型可替换，切换不改调用方**：GTCRN 与 FastEnhancer-M 同接口，推理后端（ort / tract）可换 | D33：两个模型人耳打平、证据弱，P1 起两个都接；推理后端要能比速度与功耗（设计稿 §6 关键设计 1） | 加一个模型 = 加一个适配器文件 + 一行注册，engine 与 eval 不改；适配器自报帧长、状态、`latency_samples` |

## 二、知道了它们，我要作的是哪一个决定

crate 列表与依赖方向（哪些是核心、哪些是适配层），以及每条实时规则配哪种机器检查——AST 工具只在它能把一条规则变成机器可查、或消掉成批重复代码时才采用。

## 四、我的预判（请证伪）

| 我怀疑 | 请核实 |
|---|---|
| Rust 里「用 AST 做模块化」最值钱的用法不是生成代码，而是**守架构**：依赖方向检查 + 实时安全 lint | 找成熟项目实际用 `syn`/`ast-grep`/`dylint`/`cargo-deny` 守规则的出处 |
| 过程宏生成模型适配器得不偿失：只有 2–3 个模型，宏会拖慢编译、遮住代码 | 查 Rust 社区对过程宏代价的论述（编译时间、可读性） |
| 实时路径上静态分发（泛型）不是必需：每帧一次虚调用相对 GTCRN 推理可忽略 | 查音频 Rust 项目（nih-plug、fundsp、cpal 示例）的选择与理由 |
| `assert_no_alloc` 能挡分配，但挡不住锁和系统调用；需要 RTSan 补 | 查 RTSan 对 Rust 的支持现状（rtsan-standalone crate） |
| matklad 的经验是「workspace 扁平、crate 多、虚拟清单」 | 读原文确认 |
