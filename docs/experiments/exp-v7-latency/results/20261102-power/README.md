## 结论

1. **提优先级治好了「醒得晚」**：醒来迟到中位 2616 → 22 µs，最长 7046 → 68 µs（实测）
2. **没治好「算得慢」**：三档每块都约 3.02 ms，是标定值（约 0.7 ms）的 4.3 倍；能效簇频率中位约 1.1 GHz，性能簇活跃只多 1–2 个百分点（实测）。所以线程大部分时间在能效核的低频上跑（推断：由簇活跃占比与块耗时一起推出，没直接看线程在哪个核上）
3. **工作区间没把频率拉起来，原因可能是我们给的截止期太宽**（推断）：每块 `begin` 报的截止期是 8 ms，而 3 ms 就做完了；系统在低频上也能按时完成，没有理由提频。time-constraint 也一样：声明 computation 2.1 ms、constraint 16 ms，系统同样能满足。要验证，就要报真实的预算（例如截止期 1 ms），看块耗时会不会降到约 0.7 ms
4. **耗电**：三档 CPU 功耗的平均值（117–124 mW）都不高于基线（125 mW），差别在单次测量的波动之内；中位数 tc_wg 比基线高约 27 mW，但只测了 1 次，**不能下结论**。目前只能说「提优先级看不出额外耗电」（实测，单次）
5. **对延迟修复的意义**：降噪进程的推理如果也这样落在能效核低频上，每块会多出约 2.3 ms 的计算时间，直接吃掉 lead 的余量（V7 的目标是 lead ≤ 4 ms）
