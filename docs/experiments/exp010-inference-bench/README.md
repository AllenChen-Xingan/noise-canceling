# exp010 · 推理后端基准（降噪模型在 Mac 上用什么跑最快）

> 意图：人 2026-10-31 的决定（D53），原话「必须用 core ml 或者 mlx 就是所有的推理引擎如果现在的不好，我们要重新写，用rust 或者用苹果的引擎重新写，必须达到最好的效果，最快的效果」。之后又加了三条：D68「正式测速一律从 Rust 调」、D69「整机 CPU 目标 1%、上限 2%」、D70「榨干硬件、非常低能耗、轻量」。
> 本实验分两边：
> - **纯 Rust 一侧**：本文，手下 rustbe，issue #51
> - **苹果引擎一侧**：Core ML / BNNS Graph / MLX，手下 applebe，写进 `docs/research/019_apple-inference/`
>
> 两边用同一个基准程序（`bench/`，rustbe 维护）、同一份输入、同一套评测器。评测器的正本是 applebe 的 `docs/research/019_apple-inference/standard.md`。
> 本文的名字：
> - **手写版** = 纯 Rust 手写 GTCRN（后端名 `native`）
> - **手写 + Accelerate 版** = 同一份代码，矩阵乘交给苹果 Accelerate 库（后端名 `native-blas`）
> - **ORT** = ONNX Runtime 1.31（微软的推理库），CPU 单线程，产品现在用的就是它
> - **FE-M** = FastEnhancer-M（备选降噪模型）

## 一句话结论

> ⚠️ **最重要的一条**（用实时线程策略 `--qos rt` 能缓解，但单次 60 秒的波动大，还要重复测，见「实时节奏下」）：下面的帧耗时大多是「连续跑」量的。**按产品的实时节奏（每 16 ms 一帧，帧间空闲）跑，同一份手写版慢了约 7 倍**：p50 从 0.088 涨到 0.61 ms，最大 6.95 ms，10 分钟里有 6 帧超过 3 ms，CPU 占 3.2% 个核。applebe 在 BNNS 上也看到同一现象（约慢 5 倍）。推断原因是帧间空闲时降频，或被调到能效核；还没查实。所以「推理占多少核」一律要按实时节奏重测，见「实时节奏下」一节。

- **主模型 GTCRN：手写版每帧平均 0.088 ms，是 ORT（0.381 ms）的 1/4.3**
  - 和 ORT 逐值一致：SNR 134 dB；10 分钟长跑 133 dB
  - 每帧零分配；打开 + 第 1 帧 0.36 ms（ORT 第二次建会话是 11 ms，首次加载没测）
  - 挡线评测器里：`BE-PARITY`、`BE-FRAME`、`BE-MEM`、`BE-RT-ALLOC` 都过；`BE-DEADLINE` 按实时节奏不过（用的是 ui 调度等级）；`BE-IMPACT`、`BE-SIZE`、`BE-RT-SAN` 没测。详见判据表
  - **还没到 D69 的推理目标「每帧平均 ≤ 0.08 ms」，差 10%**
  - 试过两条：
    - 矩阵乘交给 Accelerate：快 4.7%，但每帧 malloc 11 次（出在 `cblas_sgemm` 内部申请工作区，换 `vDSP_mmul` 也一样），不采用
    - 快速 tanh：快 6.7%（0.0838 ms），过对拍，0 分配
    - 人定 D75 之后，这条目标只记分、不挡
- **ORT 每帧在 C++ 里 malloc 1557 次**（FE-M 1023 次；用全进程 malloc 钩子实测），不符合「实时线程不分配」。手写版是 0 次
- **tract（纯 Rust 的 ONNX 推理库）在两个模型上都比 ORT 慢**：GTCRN 慢 1.45–1.48 倍，FE-M 慢 1.78–1.80 倍。它每帧还要分配上千次，不能放在实时线程里
- **Rust 调 ORT 对 Python 调 ORT**：同一模型、逐位相同的输入，Python 的 p50 慢 5–6%，输出数值相同（最大差 0）
- **FE-M 目前最快的后端仍是 ORT**：连续跑 p50 0.38 ms。按 D75，资源以实际耗电和对其他程序的影响为准，FE-M 在这两项上都还没测。所以现在说不出它「必须换后端」，证据不足（codex 第 1 轮 #2）

以上都是本机实测：M5，macOS 27.0.1，插电，2026-11-02，每格 3 轮。

## 实时节奏下（`results/20261102-paced1/`）

- 条件：`--pace-ms 16`，37 500 帧（10 分钟），qos ui，插电，17:42–18:02，跑前负载 1.92
- 两个后端依次跑，不交替

| 后端 | p10 | p50 | p90 | p99.9 | 最大 | 平均 | 超过 3 ms 的帧 | 占几个核 |
|---|---|---|---|---|---|---|---|---|
| 手写版 | 0.20 | **0.61** | 0.64 | 0.87 | **6.95** | 0.49 | **6** | **0.032** |
| 手写 + Accelerate 版 | 0.21 | 0.44 | 0.47 | 0.66 | 4.17 | 0.39 | 1 | 0.025 |
| （对照）手写版连续跑，r5b | 0.086 | 0.088 | 0.090 | 0.13 | 0.15 | 0.088 | 0 | 约 0.0055（推算） |

- 同一份代码、同一份输入，只是帧与帧之间空了 15.5 ms，就慢了约 7 倍
- 推断：帧间空闲时 CPU 降频，或者线程被调到能效核。p10 是 0.20 ms，比连续跑慢 2.3 倍，说明连最快的帧也变慢了，不只是偶尔被打断〔推断〕
- 实时节奏下，Accelerate 版比纯手写版快约 21%，和连续跑时的排序（只快 4.7%）不一样。推断它把一部分计算放在矩阵单元上，受 CPU 降频影响小。没验证；Accelerate 每帧 malloc 11 次这个问题照旧
- **待查：为什么实时节奏下 Accelerate 版反而快 21%**（从代码和热点分布推，没跑东西，全部是〔推断〕）
  - **哪些部分换成了 Accelerate**：编码器两层卷积（`ConvF`，热点占 22%）、1×1 卷积（`Point`，11%）、DPGRNN 的两个全连接（约占 `Dp` 那 9% 的一半）。合计约占手写版时间的 38%。GRU、tanh / exp、转置卷积、LayerNorm 两版完全一样
  - **按 38% 拆账**（单位 ms）：

    | | 连续跑 | 实时节奏 | 变慢倍数 |
    |---|---|---|---|
    | 两版共有的部分（62%） | 0.054 | 0.304 | **5.6** |
    | 被换掉的部分：手写版 | 0.034 | 0.186 | 5.5 |
    | 被换掉的部分：Accelerate 版 | 0.030 | 0.086 | **2.9** |

    算法：Accelerate 版的这部分 = Accelerate 版总耗时 − 两版共有的部分，连续跑和实时节奏各算一次
  - **最可能的解释**：Accelerate 的 `cblas_sgemm` 在 M5 上走矩阵单元（SME / AMX）。矩阵单元的吞吐受核心降频的影响，比普通指令小。所以帧间空闲导致降频时，这部分只慢了 2.9 倍，CPU 上的普通循环慢了 5.5 倍。这和「降频」这个解释吻合，和「被调到能效核」也不矛盾：能效核共享同一个矩阵单元
  - **另一个可能**：手写循环一帧要读完 95 KB 权重。帧间空闲时，L1 缓存（每核 128 KB）可能被别的进程冲掉，每帧都要从 L2 重新读；`sgemm` 的读法对冷缓存更友好。这一条拆账区分不出来
  - **怎么验证**（都要名额）：
    1. 手写版在 `--qos rt` 下重跑。如果变慢倍数明显回落，说明主因是调度或频率
    2. 帧间忙等对照（applebe 的 `--spin`）。帧间不空闲时如果不再变慢，就能确认是空闲造成的
    3. 分段计时：在 `infer` 里给各层打时间戳，直接量每部分的变慢倍数，不用靠 38% 去拆
    4. `powermetrics` 看各核簇的频率和驻留（要 sudo，交给人跑）
  - **对选型的含义**：如果主因是降频，那么减少 CPU 指令数（快速 tanh、交给矩阵单元）在实时节奏下的收益，会比连续跑量出来的大。快速 tanh 版（`native-fast`）也要按实时节奏测
- **四种线程设置**（`results/20261102-rt1/`，`tools/run_rt_probe.sh`，18:55–19:01，插电）：手写版按实时节奏，每种设置跑 60 秒（3750 帧），**每种只跑一次**

  | 线程设置 | p10 | p50 | p99.9 | 最大 | 平均 | 超过 3 ms | 占几个核 |
  |---|---|---|---|---|---|---|---|
  | `--qos ui` | 0.17 | 0.39 | 0.80 | 1.42 | 0.42 | 0 | 0.027 |
  | **`--qos rt`**（实时线程策略） | 0.12 | **0.21** | 0.66 | 0.73 | 0.30 | 0 | **0.020** |
  | ui 加入音频 IO 工作组 | 0.28 | 0.62 | 0.81 | 1.03 | 0.56 | 0 | 0.036 |
  | rt 加入音频 IO 工作组 | 0.24 | 0.61 | 0.68 | 0.69 | 0.51 | 0 | 0.033 |
  | 快速 tanh 版，ui | 0.13 | 0.21 | 0.91 | 4.43 | 0.32 | 1 | 0.021 |

  - ⚠️ **单次 60 秒的波动比设置之间的差别还大**：同样是 `--qos ui`，paced1 那次 10 分钟 p50 是 0.61 ms，这次 60 秒是 0.39 ms。所以上表只能看方向，要分出高下，每种设置得交替重复 ≥ 3 轮
  - 方向上：四种线程设置里，实时线程策略（rt）最好，p50 和占用都最低。快速 tanh 版用 ui 跑，p50 是 0.209 ms，和 rt 的 0.211 ms 相当，不过它有 1 帧超过 3 ms。加入工作组反而变差。但测的时候设备没在跑音频 IO，产品里的结果可能不同（applebe 也是这个提醒）
  - 人跑过的耗电矩阵（applebe 那边，engine worktree `docs/experiments/exp010-inference-bench/apple/results/20261102-183322-rt/summary.md`）：手写版 rt 81 mW、ui 104 mW；Accelerate 版 rt 71 mW；BNNS rt 97 mW。都是单次 60 秒，背景噪声约 ±30–40 mW，同样要重复测才能下结论
- 已经要改的口径：「连续跑的平均 ÷ 帧长」不能再当 CPU 占用。各后端都要按实时节奏重测

## Rust 调用对 Python 调用（人定：「测试如果需要的话，也要知道rust 和python的差异」）

**做法**：
- Rust 侧：`gtcrn-bench ort` 先转储全部 6201 帧的输入和输出
- Python 侧：`tools/py_ort_bench.py`（onnxruntime 1.31.1，和 Rust 侧同版本）读同一份转储，逐位相同的输入
- 会话设置照上次 Python 帧耗时实验（exp001）：单线程，`ORT_SEQUENTIAL`；计时线程的调度等级同样设为 `USER_INTERACTIVE`
- Python 只计 `sess.run` 那一次调用；Rust 计时还多包含输入输出拷贝，对 Rust 略不利
- 两边交替跑 3 轮。数据：`results/20261102-pyrs1/`

| | p50 | p99 | p99.9 | 最大 | 平均 |
|---|---|---|---|---|---|
| Rust 调 ORT | 0.377–0.380 | 0.407–0.411 | 0.444–0.550 | 0.552–0.666 | 0.378–0.382 |
| Python 调 ORT | 0.399–0.401 | 0.427–0.434 | 0.445–0.558 | 0.576–0.672 | 0.400–0.401 |
| Python ÷ Rust（按轮） | 1.055–1.060 | 1.041–1.067 | 0.94–1.26 | 0.92–1.22 | 1.049–1.059 |

- Python 的输出和 Rust ORT **数值相同**（最大差 0）
- **差多少**：中位数和平均都是 Python 慢 5–6%，约 0.02 ms。推断这部分是 Python 把 numpy 数组转成 ORT 张量的开销
- **尾部**（p99.9、最大）分不出谁快：3 轮里各有胜负，样本太少
- 结论只限这一次观测：一个模型（GTCRN）、ORT 一个库、3 轮，中位数和平均值上 Rust 比 Python 快 5–6%。尾部的比值在 0.92–1.26 之间，没有定论
- 归因还不能下（codex 第 1 轮 #8）：两边的计时边界不同（Python 不含拷贝），输出分配策略也不同（Python 每次新建输出，Rust 预先分配）。要拆开，得做一组边界相同、分配策略也相同的对照

## 还能怎么更快（D69：推理每帧平均 ≤ 0.08 ms）

> 口径更新（人定 D75）：资源以「实际耗电 + 对其他程序性能的影响」为准，活动监视器的 CPU% 只作参考。所以「连续跑每帧平均 ≤ 0.08 ms」这条只记分、不挡，本轮不再专门为它做优化。本节留作以后的路线图。

**手写 + Accelerate 版实测**（`results/20261102-blas1/`；17:43；和手写版交替跑 3 轮）：

- 只快 4.7%。小矩阵实测能省 10 µs，整网只省了约 4 µs。推断原因：只有 1×1 卷积、编码器卷积、DPGRNN 全连接换成了 Accelerate，GRU 和转置卷积没换；另外 im2col 本身要额外搬数据
- Accelerate 内部每帧 malloc 11 次，过不了 `BE-RT-ALLOC`，所以**不采用**。代码留在 `native-blas` 作对照
- **这 11 次出在哪**（`results/20261102-malloc1/amx.jsonl`，malloc 钩子加调用栈，19:05 实测）：
  - 调用链：`cblas_sgemm → APL_sgemm → APL_sgemm_QR → posix_memalign`。Accelerate 每调一次，就为这次矩阵乘申请一块对齐的工作区
  - 只有较大的三种形状会分配，每次调用 1 次：1×1 卷积 24→16（每帧 6 次）、DPGRNN 全连接（4 次）、编码器第一层（1 次），合计 11 次，正好对上
  - 较小的两种形状（1×1 卷积 16→8、GRU 输入投影 8→12）不分配。推断：只有走 `QR` 那条路径时才申请工作区，走哪条路径由矩阵大小决定
  - **`vDSP_mmul` 在同样三种形状上也是每次分配 1 次**，换成它没用。速度和 `cblas_sgemm` 差不多（每帧合计 12.5 µs 对 12.4 µs）
  - 据我所知，cblas 和 vDSP 都没有让调用方传入预先分配好的工作区的参数〔推断，没逐个读头文件核实〕
  - 剩下两条路，都没试：
    - (a) 用 BNNS：预先建好滤波器或图，执行时不分配（官方 WWDC24 说 BNNS Graph 执行不分配），这归 applebe 那一侧
    - (b) 把矩阵切小，让每次调用都落在不分配的路径上。这靠的是 Accelerate 的内部行为，系统一更新就可能失效，不建议
  - 大总管已定：默认用纯手写版（0 分配）。Accelerate 版只有同时满足「0 分配」和「交替重复测仍更省电」才翻盘。按本节结果，cblas / vDSP 这条路满足不了「0 分配」

## 口径（两边共用，已和 applebe 对齐）

- **输入**：`resources/gtcrn/test_wavs/mix.wav`，16 kHz 单声道，610 帧
  - 基准：1 帧冷启动、200 帧预热，再计时 6000 帧；音频不够就循环，STFT 中途不重置
  - 对拍：默认用整段音频，不循环；`--frames N` 时循环
  - GTCRN 的一帧：同一个 STFT（`vdn-dsp`，512 点 / hop 256，sqrt-hann）出来的 257 个复数频点，16 ms
  - FE-M 的一帧：160 个样本，10 ms（图里自带 STFT）
- **对拍**（逐值一致，沿用上次 Rust 对拍实验 exp004 的做法）：
  - 同一份输入，ORT 和被测后端各从零状态顺序跑完，比较每帧的全部输出值
  - 报这几项：
    - 最大绝对差
    - 整段 SNR，即 10·log10(Σref² / Σ差²)
    - 逐帧 SNR 的最小值 `min_frame_snr_db`：只统计参考能量 ≥ 全段平均帧能量 1e-4 的帧，专看安静段
    - 非有限值个数
    - `first_bad`：第一个差 > 1e-3 或出现 NaN 的位置
  - `first_bad` 不为 None 的「更快」不算数
- **计时**：只计一次 `infer` 封装调用，包括输入输出拷贝和缓存回灌，不包括 STFT
- **单线程**：
  - ORT：intra / inter = 1、不自旋、`PreferCPU`、`ORT_ENABLE_ALL`，和 `src/models/src/session.rs` 一样
  - tract：不设线程池
  - 手写版、Accelerate：单线程调用
- **调度等级** `--qos`：默认 `ui`，即 `QOS_CLASS_USER_INTERACTIVE`
- **字段**：
  - `p10_ms` / `p50_ms` / `p90_ms` / `p99_ms` / `p999_ms` / `max_ms` / `mean_ms`：分位数按 round((n−1)·p) 取
  - `ort_env_ms`：ORT 环境初始化加读输入形状，计时前做，不算进 `open_ms`
  - `open_ms`：建模型；`first_frame_ms`：第 1 帧
  - `cpu_over_wall`：计时段 CPU 时间 ÷ 墙钟时间
  - `rust_allocs_per_frame`：Rust 分配器次数，不含 C / C++
  - `process_allocs_per_frame`：加 `--count-malloc` 时，用 `malloc_logger` 钩子数全进程分配；不加时为 null。钩子会拖慢分配，所以计数和计时分开跑
  - `footprint_before_mb` / `footprint_warm_mb` / `footprint_end_mb`：`ri_phys_footprint`，即活动监视器的「内存」列。分别在加载前（输入帧和 ORT 环境已在内存里）、预热完、跑完时读
  - `pace_ms`：大于 0 时按实时节奏喂帧
- **转储** `--dump-io <前缀>`：写出全部帧的输入和 ORT 输出（小端 f32），外加一份 json 记录 sha256。applebe 的程序和 Python 对照都吃这一份

## 选哪个 Rust 推理库：tract

依据来自子代理调研（2026-11-02）。来源等级：源码 / 官方 / 公开实测。

| 库 | 版本 | GRU | ConvTranspose（转置卷积） | LayerNorm | 结论 |
|---|---|---|---|---|---|
| tract | 0.23.9（2026-10-15） | 有〔源码〕 | 有 | 有 | 选它，理由见表下 |
| rten | 0.27.0 | 有 | 有 | 有〔源码〕 | 第二候选；没有小模型的公开实测，本轮没测 |
| burn-onnx | 0.22.0 | 有 | 有 | 有〔官方算子表〕 | 把 ONNX 生成 Rust 代码；小算子在 CPU 上的性能没有数据，本轮没测 |
| candle-onnx | 0.11.1 | **无** | **无** | **无**〔源码〕 | 跑不了 GTCRN，排除 |

选 tract 的理由：
- tract 自己的每晚基准里就有 GTCRN 流式单帧模型（`ci/benches.toml` 第 546–552 行），状态张量的形状和我们的一样
- 公开实测 M1 Max 单线程每帧 0.294 ms
- 2026-08 至 10 月专门做了 GRU 融合〔官方 CHANGELOG〕

实测下来 tract 没赢 ORT。结论只能说「tract 没赢 ORT」，不能推到「Rust 推理库都赢不了」：rten 和 burn 本轮没测。

tract 公开的 0.294 ms 和本机的 0.55 ms（p50）对不上。复用状态和每帧新开状态，两次实测的值摆在这里：复用时 p50 0.552 ms、每帧分配 2224 次；新开时 p50 0.553–0.564 ms、分配 2247 次（见 `bench-extra.jsonl`）。但复用版从第 1 帧起就算错了，两版走的计算路径不同，所以这组数**不能**用来算新开状态的代价（codex 第 1 轮 #7）。要单独量，得另测建状态和销毁状态各要多久。这个差距的原因没查。原因没查。

## 踩到的坑

1. **tract 复用同一个运行状态会算错**：
   - 现象：第 0 帧对，第 1 帧起错，SNR 19.4 dB（`results/20261102-r5b/parity.jsonl` 里的 `tract-reuse-known-wrong`）
   - 原因〔读源码，自审查到〕：tract 把 ONNX 的 GRU 转成 `GruSeq` 时设了 `reset_every_turn: false`（`tract-onnx-0.23.9/src/ops/rec/gru.rs:72-74`）。这样一来，除了第一次调用，GRU 都忽略输入的初始状态，接着用上一次的末状态（`tract-core-0.23.9/src/ops/gru_seq.rs:180-185`）。GTCRN 频率方向的 GRU 每帧都要从零开始，所以出错
   - 办法：每帧新开一个状态，就和 ORT 一致（130.4 dB）。代价见上一节；设 `EXP010_TRACT_REUSE=1` 可以复现错误
   - 要不要报给 tract 上游，待人定
2. **tract 不支持 FE-M 图里的 `SplitToSequence`**：
   - 办法：`tools/fem_strip_seq.py` 把 8 处「`SplitToSequence(axis 0, keepdims 0)` 接 `SequenceAt(常数 0)`」换成等价的 `Gather`
   - 改后的图在主目录 `_tmp/20261102-exp010/fastenhancer_m_noseq.onnx`
   - 已证明改写等价：ORT 跑原图对 ORT 跑改写图，数值相同（最大差 0）
3. **别的会话的重活干扰计时**：r1 有 miri 并行；r2、r3 和别处一次编译重叠（16:31–16:32），r2 有一轮 ORT 最大值到了 62.9 ms。这几版只作参考，不进结论；原因写在各自的 `env.txt` 里
4. **r4 → r5b 口径变了**，所以 r4 的数字不再用：
   - 加了调度等级，帧耗时多报 p10 / p90
   - 「打开」不再包含 ORT 环境初始化：r4 里 ORT GTCRN 打开 18 ms，r5b 是 10 ms 加上单列的 17 ms 环境
   - tract FE-M 的「打开」不再含 ORT 建会话
   - 手写版换成了去分支后的版本
   - r4 的结论方向和 r5b 一致
5. **exp004 量的 ORT p50 是 0.70 ms，本轮是 0.38 ms**：
   - 主要原因推断是机器状态不同。依据：exp004 的 FE-M 计时不含外部 STFT，也从 0.67 ms 降到 0.38 ms，降幅和 GTCRN 一样
   - exp004 计时包含 GTCRN 的 STFT（`src/models/src/gtcrn.rs:88-104`；计时取 `src/engine/src/engine.rs:270-272` 的 `last_model_time`），但这部分占多少没量
6. **r5 刚开头就因脚本 bug 退出了**：`ps | head` 在 `pipefail` 下触发 SIGPIPE，没跑任何对拍或基准，目录里只有一份注明原因的 `env.txt`。正式版是 r5b

> - standard.md 要求：线程设置用 D74 默认（rt）、多轮交替、报 CPU + GPU + 神经引擎的总功率增量
> - 本脚本最初是：ui、每个后端只跑一次、只采 CPU 功率
>
> 已改成：采 CPU / GPU / 神经引擎三项，线程设置默认 rt，3 轮交替。人实际跑过的那次是 applebe 那边的脚本（`apple/results/20261102-183322-rt/`），选默认后端以 applebe 那边按 standard.md 跑的数为准。

`tools/power_run.sh` 要 sudo，由人来跑：

```sh
sudo bash docs/experiments/exp010-inference-bench/tools/power_run.sh 20261102-p1
```

- 跑法：按实时节奏，每个后端各跑 60 秒，同时用 `powermetrics` 采 CPU 功率；另加 60 秒空闲作对照。约 8 分钟
- 结果写进 `results/20261102-p1/power/summary.txt`
- 每帧耗电 ≈（后端平均功率 − 空闲平均功率）× 帧间隔

## 转交（超出 rustbe 范围，报大总管）

手写版要进产品（`src/models`），自审列出还缺这些（`review-native` 的 P1、P2）：
1. **过不了 `vdn-models` 的禁 panic 规则**：clippy 报 142 处越界检查；构造代码和实时代码混在同一个 `impl` 块里
2. **缺接入件**：没有 `Model` 适配器（STFT 分析 → 推理 → 合成），没有 `AnyModel` 变体，没有进 CI 的测试（对拍、零分配、reset、故障注入）
3. **输入没有防护**：入口不检查非有限值和长度。NaN 进来后会一直留在循环状态里，直到 `reset` 才清掉
4. **权重在仓外**：加载时不校验 sha256。权重只有约 95 KB，GTCRN 是 MIT 许可，可以考虑直接编进程序
5. **对拍的参考是 ORT，不是 PyTorch**：要宣称「和原模型等价」，还要补一次手写版对 PyTorch 流式版的逐帧对拍
