## 人的原话

## 一、做 AST 是不是为了降复杂度
是。005 引写匠原话：目的是「防止产品中后期复杂度失控」【读】。它降复杂度靠三点：
1. **一份表示，多处使用**：离线评测、实时运行、会话记录、可视化都从同一张处理图来，不各写一份
2. **扩展 = 加叶子**：新增一种处理 = 加一种节点类型，不改主干代码
3. **能被机器查**：结构是数据，就能被工具搜索、比对、校验

## 二、现在的复杂度从哪来（实测）
| 现象 | 数 | 来源 |
|---|---|---|
| 同一组类型的「镜像」副本 | 3 个 crate、12 处（`src/speaker/src/types.rs` · `src/polish/src/mirror.rs` · `src/scene/src/mirror.rs`） | 【测】grep「镜像」 |
| 一个参数（衰减下限 `floor_db`）出现的文件数 | 20+ | 【测】grep |
| 手写、无 schema 的数据文件 | 评测任务 4 份 JSON（`src/eval/suite/`）· 场景参数表文本 · Config JSON | 【读】 |
| 跨进程结构只有 Rust 一边定义 | 共享内存头（版本 2，刚加 4 个字段，rs-entry 的字面量要跟着补） | 【读】 |

## 三、提议：schema 是「结构的正本」，Rust 类型和数据文件都要对得上它
| 要 schema 的东西 | 交叉校验（CI 里机器判） |
|---|---|
| 处理图（节点类型 · 参数 · 范围 · 版本） | Rust 节点类型 ↔ schema 字段与范围一致；处理图文件过 schema |
| 参数组 / 场景参数表 / 我的配置 | 参数范围只写一处；Rust 的范围校验与 schema 的 min / max 同源 |
| 会话记录 / 决策日志 | 事件种类 Rust ↔ schema 一致；录下的日志文件过 schema |
| 共享内存头（跨进程、给虚拟麦克风） | 字段偏移、大小 Rust（`offset_of!`）↔ schema 逐项比对；版本号变了 schema 必须变 |
| Config · 评测任务清单 | 文件过 schema；Rust 反序列化后再序列化与原文件等价 |
| 模型接口（输入输出名字、形状） | ONNX 文件实读 ↔ `ModelKind` 声明 ↔ schema 三方一致 |

**机制（AI 建议，技术细节由 AI 定）**：Rust 类型是源头，由 `xtask` 导出 schema 文件并提交进仓；CI 重新导出并与仓里的比对，不一致就红（照 ADR 004「要生成就用 xtask 生成、提交、加一致性测试」，不在构建时生成代码）。核心 crate 仍不引 serde（规约 §2.2 规则 1）：字段描述写成 `vdn-types` 里的常量表，导出与校验放在 tool 档的 crate。三个镜像副本删掉，改直接用 `vdn-types`。
