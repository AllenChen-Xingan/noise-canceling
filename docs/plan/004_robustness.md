# 004 · 极端情况与抗压：从「一个人稳定」到「一百万人稳定」

> 2026-10-30 大总管起草，**AI 方案，待人过目**。起因：人问「当用户量或者各种东西增加到 1000000 人……这种极端的情况，我们的软件会遇到什么，在这样的情况下，我们的架构如何也保证完全可以，抗压力」。

## 一、先分清：我们的「规模」和文档软件不一样

文档软件的规模是**数据量**：一千万个文件、十亿字符，压力集中在一台服务器或一个索引上。
我们是**本机实时处理**：每个用户的 Mac 只处理自己这一路麦克风，没有服务器，一百万人不会把哪台机器压垮（D 意向书「不联网、不上传」）。

**一百万人带来的真正压力是「概率」**：
- 一个人每天开会 1 小时 = 每秒 100 帧 × 3600 秒 = 36 万帧
- 一百万人每天 = **3600 亿帧**
- 所以「十亿帧才出一次」的毛病，在一百万人里**每天发生约 360 次**。一个人测一辈子都碰不到的 bug，上线第一天就会被几百个人碰到。

**结论**：我们要抗的不是吞吐量，而是**长尾**——罕见的设备、罕见的声音、罕见的时序、罕见的系统状态。

## 二、一百万人会遇到的极端情况

| 类 | 例子 | 一旦出事，用户感受 |
|---|---|---|
| **时间** | 一场会开 8 小时；电脑一周不关机；睡眠唤醒几百次 | 慢慢变卡、内存涨、模型状态漂移、突然断音 |
| **设备** | 蓝牙耳机中途掉线、切到 16 kHz；USB 麦热插拔；外接声卡几十种；AirPods 自动切换 | 没声音、爆音、延迟越来越大 |
| **算力** | 老款 Mac、低电量模式、过热降频、同时在编译 / 渲染视频 / 开 50 个浏览器标签 | 推理来不及 → 断续 |
| **声音** | 极吵（施工、地铁）、极静、对着麦大喊（削波）、背景音乐、几百种口音与语言、儿童与老人的声音、多人共用一台电脑 | 吃字、怪声、把人当噪音压掉 |
| **软件环境** | 每年 macOS 大版本更新改动音频系统；Zoom / Teams / 浏览器各自改采样率、独占设备；杀毒软件拦驱动 | 设备消失、装不上、崩溃 |
| **数值** | 极小数（denormal）让 CPU 变慢百倍；NaN 一旦进入循环网络状态会一直坏下去 | 突然很卡、之后一直输出噪音或静音 |
| **人** | 不会装、装错设备、忘了开、想卸载 | 「这软件不好用」 |

## 三、架构上怎么保证（多数已在设计里，标出还缺的）

### 1. 出事时永远有原声（最后一道防线）
- 已定：两层送原声（D03 · ADR 005）——模型单帧出错引擎切原声；推理进程卡死或崩溃送音进程切原声
- **要补**：看门狗（推理进程心跳停了多少毫秒就切原声并重启它）；**任何失败路径都走原声，绝不走静音**；连续失败自动降级到「只做直通」并告诉用户

### 2. 不让小错长成大错
- 已定：实时三档（ADR 002）；IO 回调零分配零锁，机器检查
- **要补**：
  - 模型状态定期「体检」：NaN / 超范围 / 输出能量异常 → 复位状态（P1 已有故障注入，要扩成长时运行下的自愈）
  - denormal 统一刷零（FTZ/DAZ）
  - 有界一切：缓冲有上限、重试有上限、日志有上限；内存只在启动时分配

### 3. 长尾要靠「造出来」测，不能等用户撞
- **浸泡测试（soak）**：连续跑 24–72 小时，盯内存、延迟、CPU 是否漂移
- **混沌测试**：自动化地拔插设备、切采样率、睡眠唤醒、把 CPU 打满、杀推理进程——每种都必须「最坏是原声」
- **模糊测试 / 性质测试**：随机、极端、损坏的音频（全零、满幅削波、NaN、超长静音、极短片段）喂给每一层
- **声音多样性测试集**：按口音、语言、年龄、性别、麦克风、房间分格，每格都过吃字率门禁（004 回归门禁形状已定）
- **老机器**：CI 和发布前在最慢的支持机型上跑（D07：Apple Silicon、macOS 14.2+）
- **确定性回放**：任何一次异常都能用记录下的输入在离线版复现（离线与实时同一份代码，已定）

### 4. 上线后看得见，但不偷看
- 意向书定了不上传音频，所以**没有遥测**是默认。替代：
  - 本机诊断日志（只记计数和时间，不记声音），用户一键导出、自己决定发不发
  - 可选的崩溃报告（用户同意才发，不含音频）
  - 用户反馈通道（D27）

### 5. 发布控制
- 分批推送更新（先 1% 测试者，再全量）；一键回滚到上一版
- 每个 macOS beta 出来就跑全套测试，正式版发布前修好
- 模型和代码一起签名，防止被替换

## 四、建议下一步

1. 把第三节的「要补」列进路线图：送原声看门狗与自愈进 M1；浸泡、混沌、模糊测试进阶段 B 的评测飞轮；多样性测试集随评测一起建
2. 开一条调研线「实时音频软件的可靠性工程」：看 Krisp、Zoom、WebRTC、游戏语音、Apple 自己的音频团队、专业音频插件厂商公开讲过的事故与做法；以及大规模客户端软件（浏览器、操作系统）怎么做崩溃统计、分批发布、长尾测试
3. 人要定：要不要有「用户同意才发」的崩溃报告（与「不上传」的边界）
