# 006 · 版本规划：0.x 每版一个目标，1.0 正式发布

> 2026-10-31 大总管起草，**AI 方案，待人过目**。人原话：「就是这个项目其实还挺大的 / 就是我如果要吧ta 分成几个大版本 / 就是1版属于正式发布的版本 / 然后现在每个0.x版是一个功能或者一个特定的目标 / 这个你打算怎么安排路线图」
> 与 `002_roadmap.md`（阶段 A–C · M0–M4）的对应写在每行；以后路线图以本文的版本号为主线。

## 规则
- **一个 0.x = 一个能验收的目标**：有「机器判」（CI、评测门禁）和「人判」（盲听 / 真会议）两种完成标准，都过才打 tag
- 每个版本在 GitHub 上是一个 **milestone**，该版本的 issue 都挂上去；完成时打 `vX.Y.0` tag、写 `state/changelog.md` 一条（变了什么 · 为什么 · 对你意味着什么）、workspace 版本号同步
- 版本内的小修用 `0.x.y`
- 三把尺子在每个版本都不许变差（意向书）；延迟 ≤ 45 ms（D32）、察觉不到占用（D37）、无云端（D39）是所有版本的硬约束

## 版本之间的依赖
- 0.2 与 0.3 可以部分并行（模拟环境在 0.2 已起第一版）
- 0.4 起需要你装 BlackHole；0.8 起需要开发者账号
- 0.6 依赖 0.5 的会话记录与配置版本化；0.7 依赖 011 调研与 0.2 的声纹
- 训练（D29）不在任何 0.x 的必经路径上；若 0.7 现成方案不够，才在 0.7 / 0.9 之间插入

## 要人定
1. 这个切法行不行，尤其 0.3（评测）放在 0.4（实时）之前
2. 1.0 的门槛：测试者用多久、多少人、哪些场景必须过
3. 要不要现在就在 GitHub 上建 0.2–1.0 的 milestone，并把已有 issue 挂上去
