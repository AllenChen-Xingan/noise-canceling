## 规则 1：一词一义，同一事物始终用同一个词

**违规次数估计**：约 15 处以上，其中 4 处造成了实际误读或返工。

**最有力的例子**
1. **「40 ms 延迟」有三种算法，大总管和助手都算乱了**（867e4cc6，约 244–261 行）。大总管说：「口径对齐：40 ms 出自 DNS Challenge，指『算法延迟』= 窗长 + 前瞻，不含管线。你把『管线+模型 65–70 ms』跟它比是两种口径。」随后又改口：「你对，我对过 PDF 原文了，DNS 口径是窗长+步长+前瞻……账本已更正。」怀疑派审稿也指出，libDF 代码里的延迟又是第三种算法（30 ms 和 40 ms 的差别）。**后果**：协调层来回纠正两次，账本改过一次，取舍卡要拆成三列。
2. **同一个代价写了三个数**（867e4cc6，产品派，约 286 行）：「同一个代价在 :15 写 60、:60 写多 45、:106 写 70，人看到三个数。」
3. **「过预算」可以读成两个相反的意思**（b38be9ff，怀疑派，约 327 行）：「『过预算 → 换主模型』按上下文是『通过』，但字面也能读成『超过』……拍板时容易读反，建议改成『在预算内』。」
4. **「p1」和「P1」撞名**（2f59348f，视角 C，约 235 行）：「『p1』（指人/会话）和『P1/P3』（指阶段）混着用。」收尾报告里两者紧挨着出现：「这些数是估算，P3 要实测……我给 p1 的推理用法改过一次」（约 342–343 行）。P0–P3 还同时表示严重级别，所以「P1」在这些会话里有三个意思：会话名、阶段、严重级别。
5. 其他同义词混用：「延迟账 / latency ledger」「送原声 / 旁路 / bypass」「三件保命 / 保命」「抄思路 / 学思路」（视角 C 指出「抄」字外行会读成复制，约 225 行），以及「送音进程 / 推理进程 / 降噪线程 / 推理线程」之间是什么关系没有交代（约 235 行）。

**对人造成困惑的证据**：大总管本身就被「口径」绕进去，纠正一次又撤回（例 1）。三个审稿代理分别指出同义或多义词会让人读反（例 2–4）。

**建议写进 CLAUDE.md**：同一个量只用一个名字和一种算法；数字第一次出现时写明算法（例如「算法延迟 = 窗长 + 前瞻」），全文只引用这个名字，不换说法。

## 规则 2：黑话、缩写、自编代号要在第一次出现时定义

**违规次数估计**：每份收尾报告都有 5–15 个没定义的代号，7 份合计约 70 个。这是本组最普遍的问题。

**最有力的例子**
1. **自审代理直接列出看不懂的词**（2f59348f，视角 C，约 234 行）：「黑话没有解释，产品人读不懂：SPSC、wait-free、FTZ/非正规数、IOProc、HAL、cdylib、workgroup、EP/ANE、soundness、arena、RAII、Exhibit B、tier 2。」还有「D03/D31/D33、M0–M1、『命门』也没有指向出处」。
2. **一句话总结 30 秒内看不懂**（b38be9ff，产品派，约 194 行）：「『门控』『声纹门控』『M5』『预算 3–5 倍』『注册基础设施』都是黑话，而且没说用户会体验到什么。」
3. **代号的定义在仓库里根本找不到**（c06dbb7a，合规审查，约 126、140 行）：「`docs/plan/001` 只到 D27，D39、D42、D47 在 001 里找不到定义。」收尾报告仍然写「照 D19 处理」「超出原来定的 15–20 GB 上限（D22）」「013 待拍板的 #4b」（约 292–302 行）。V-SIM-GATE、SWLAT、V-EAT-ASR、L0 这些指标代号也没解释（约 133、159 行）。
4. **收尾报告里的自造词**（7dac8cc0，约 433–453 行；867e4cc6，约 474–495 行）：「每把尺子……分 CI 层和本机层……回归门禁」「三条命门全过的只有 GTCRN」「另两把尺子不能变差」「说话人门控（M3）」。「尺子 / 命门 / 门禁 / 格子」是项目内部的比喻，从来没有对人定义过。

**对人造成困惑的证据**：3 个会话的自审代理都独立判定这些词「人读不懂」（例 1–3）。例 3 说明这些代号连协调层都查不到出处。

**建议写进 CLAUDE.md**：给人看的文字里，每个代号（D 编号、P/M 阶段、exp 编号、#题号）和项目比喻（尺子、命门、门禁）第一次出现时，在括号里用一句白话说明它是什么；查不到定义的代号不要写。

## 规则 13：中英混写，或者整段换成英文

**违规次数估计**：助手轮次里全英文的有 102 条（共 260 条，占 39%）。b38be9ff 整场英文，包括给人的收尾报告和「七个待人拍板」。ce3ff3d1 有 46/59 条是英文，收尾报告也是英文。

**最有力的例子**
1. b38be9ff 收尾（约 376–399 行）：「**Seven decisions are waiting for a human** … whether to accept a voice model trained on the VoxCeleb research dataset …」。这是中文项目，人要在这份报告上拍板，报告却整段英文。
2. ce3ff3d1 收尾（约 607–620 行）：「**Decision for the human:** make the 96-frame mic buffer the P3 target? …」，待人拍板题也是英文。
3. 同一会话里中英来回切换：867e4cc6 约 231–268 行，「Now the self-review: three subagents…」「I'll write that into the table when I make the edits.」，前后都是中文。7dac8cc0 约 32、44 行，「Now continuing…」「Status: repo URLs confirmed…」。
4. 一句里夹英文词，而中文有现成说法：「hop」「worktree」「名额连用做推理对拍」「Stage 签名」「smoke」等。

**对人造成困惑的证据**：没有人直接抱怨，因为本组没有真人消息。但待人拍板的题目是英文，直接加重了人读题的负担。语言来回切换也说明模型在长会话里没有守住输出语言。

**建议写进 CLAUDE.md**：所有给人或大总管看的文字一律用中文，包括状态行、收尾报告和待拍板题；英文只保留代码标识符和专有名词，并用反引号括起来。

## 规则 12：说准确，用具体数字和单位代替模糊说法

**违规次数估计**：约 10 处。正面例子更多，本组助手大体做得好。

**问题例子**
1. 「算力是预算的 3–5 倍」「确定变差」被写成定论（b38be9ff，怀疑派，约 307 行）。依据只是 Xeon 云主机上的平均 RTF，「拿的是『平均占用』去比『最坏一帧』，口径不同」。
2. 「Rust 省下的只是 numpy 那一点」「同一时段比较」（15a3dcf1，约 420–421 行）：说法超出了测量能支持的范围。
3. 「效果明显弱一档」（867e4cc6，约 479 行）：没给数字。

**正面例子**：「本机最坏一帧 0.89 ms，只占 10 ms 周期的 9%」（867e4cc6，约 476 行）；「回调频率从约 5.3 ms 变成 2 ms 一次，约 2.7 倍唤醒」（ce3ff3d1，约 528 行）；15a3dcf1 收尾的计时表。

**建议写进 CLAUDE.md**：给结论时带上数字、单位、测量条件（机器、平均还是最坏）；没有数字的程度词（明显、大概、确定）要么换成数字，要么标「推断」。

## 规则 10：区分事实和推断，用简单时态

**违规次数估计**：约 8 处推断被写成事实，都被自审抓到。

**例子**
1. 延迟账「IO 缓冲并入攒 hop」本来是推断，测试却把它钉成了事实（ce3ff3d1，约 397–399 行）：「测试把推断钉成事实……对外口径应该报 47 ms」。后果：对外报的数从 41.67 ms 改成 47 ms，从「达标」变成「超预算 2 ms」。
2. 「96% 帧有声」的原因解释错了（15a3dcf1，约 413 行，P0）。助手自己承认：「我之前的原因解释是错的。」
3. 「用转写造逐帧真实标签，不需要教师模型」（c06dbb7a，约 158 行，P0）。
4. 「VoxLock 自己也压环境噪音」没有出处（b38be9ff，约 312 行）。

**正面例子**：p1、align 的收尾报告明确写了「只做了波形检查，没用耳朵听」「这些数是估算，P3 要实测」「All three are untested estimates」。

**建议写进 CLAUDE.md**：每条结论标明来源（实测 / 读源码 / 推断）；推断不进测试断言，也不进一句话结论。

## 规则 8 和 9：段落一段一个主题、首句点题；并列项用列表或表格

**违规次数估计**：中间状态行基本合格（1–2 句）。收尾报告结构较好，但有 2–3 处一句塞进多个概念。

**例子**
- 产品派（867e4cc6，约 298 行）：「:14 一句话塞了 STFT/OLA、state、4 帧对齐，人一页读不懂……改法：首句先写延迟。」
- 产品派（b38be9ff，约 194 行）给了一个好的改写样本：「能直接只留你声音的开源模型只有一个，太费电；先做一版『只在旁人单独说话时把声音压低』的……」

**正面例子**：几乎每份收尾报告都是「结论 → 列表 → 待拍板编号 → 文件路径」的结构。7dac8cc0 的「尺子 × 主指标 × 交叉」表、c06dbb7a 的「数据集 × 管什么 × 许可」表都清楚。

**建议写进 CLAUDE.md**：收尾报告第一句给结论（做完没有、能不能用），然后用列表或表格；一个句子只放一个技术概念。

## 规则 3、4、7：句子长度、一句一事、名词堆叠

**违规次数估计**：中文句子按标点切分后超过 45 个汉字的只有 8 句（共约 420 句）。长度本身问题不大，问题在于**密度**：短句里堆了三四个名词。

**例子**
- 「推理线程按软实时管（硬实时回调在送音进程，只碰环形缓冲）」（同级会话的话，助手照转）。
- 「场景参数表（定长、可整表按值热更新、文本可序列化）」（ce3ff3d1，约 70 行）。
- 「模型接口 + 智能体部件骨架 + 延迟账」（ce3ff3d1，约 58 行）。
- 名词堆叠：「旁路交叉淡化时长」「近讲 + 时间戳 → 真实逐帧标签」「端到端附加延迟」「单线程推理预算」。

**建议写进 CLAUDE.md**：中文一句不超过约 40 个字，只说一件事；不要连写 3 个以上的名词修饰语，必要时拆成「X 的 Y」，或者另起一句解释。

## 规则 6：指令用祈使句，条件放前面（「如果 X，做 Y」）

**违规次数估计**：待拍板题里约 5 处默认值或条件写得不清楚。

**例子**
- 默认值和条件互相矛盾：867e4cc6 的 #1 默认 A、#5 默认「不改」（实现派和怀疑派都指出，约 284、398 行）。
- b38be9ff 的默认值组合起来，会让核心功能永远停在第 1 步（产品派 P0，约 176 行）。
- c06dbb7a 的默认值「不拍板也会自动越过一条已拍的决定」（约 131 行）。
- 正面例子：c06dbb7a 收尾「建议约 20 GB……等于改那条决定；不拍板就默认只下几 GB」，条件和后果都写明了。

**建议写进 CLAUDE.md**：每道待拍板题写成「如果你不回答，默认 X，后果是 Y」，并检查各题默认值组合起来不互相矛盾、不越过已有决定。

## 规则 11：警告放在它针对的那一步之前，并写出后果

**违规次数估计**：少。助手在动手前就报了风险，例如「P.808 浅克隆完是 1.1 GB，超过了 1 GB 要先问的线」（7dac8cc0，约 59 行）。反例是 `git mv` 违规事后才报（ce3ff3d1，约 227 行：「Note to self: I used `git mv` there」）。

**建议写进 CLAUDE.md**：要做会越线的操作（大下载、git 写、改范围外文件），先说清楚「做了会怎样」再做；做完才发现越线的，放在报告的显眼位置。

## 规则 5：主动语态、主语明确

**违规次数估计**：少。多数句子主语清楚（「大总管负责清理」「我这边不做任何 git 写操作」）。问题集中在「已改完 / 已修」这类省略主语的句子，读者分不清是谁改的：hook、大总管还是本会话。例如「这次修改已经自动提交（819435e）」就把动作归给了 hook。

**建议写进 CLAUDE.md**：涉及多方（大总管、hook、同级会话、子代理）的动作，写明是谁做的。

## STE 以外、影响对话质量的问题

1. **一次抛出太多待拍板题，而且有些是纯技术题。** 7dac8cc0 留了「11 题待人拍板」。867e4cc6 产品派指出「#2、#3 是纯技术细节，可以由 AI 先定」。2f59348f 视角 B 说「第 4 题（CoreML 实验）是技术判断……不该问人」。b38be9ff 产品派说「#2 里的 fbank 口径、Praat 先例……普通用户答不了」。这些都是人不该收到的问题。
2. **拍板题用技术口径出题，没有翻成人能感知的后果。** 867e4cc6 产品派 P0（约 278 行）：「拍板 #1 问的是『用哪种口径算延迟』……人看不懂。人真正要定的是『对方多晚听到你说话』。」修改后的版本（约 484–490 行）改成了四档毫秒数加「超过国际电信联盟建议的 150 ms」，这是一个**好的改写示范**。
3. **报告里讲内部流程，喧宾夺主。** 收尾报告常写「三个对抗视角自审，2 个严重、10 个较重已改完」「一个小意外：脚本编成了 008 号」「Rule slip: git mv」，这些占了人的阅读时间。可以压成一行放到文末。
4. **对同一份报告给出多个版本的数。** ce3ff3d1 先报 41.67 ms，再改成 47 ms，又提出 43.67 ms。三个数都写进收尾报告是对的（有解释），但人第一眼会被三个数搞糊涂。建议首句只放当前结论数。
5. **状态播报过多。** 每个会话都有十几条「等 X 回来」「正在等」这类一句话状态（例如 867e4cc6 约 237、254、268、305、372 行全是在等审稿人）。对大总管来说是噪音。

## 正面例子（清楚的写法起了作用）

## 按影响排序的前 8 条规则（只针对本组文件）

1. **规则 2：代号和比喻要定义**。每份收尾报告都有，3 个自审代理独立判定「人读不懂」，D39/D42/D47 连定义都找不到。
2. **规则 1：一词一义、一个量一种算法**。「40 ms 口径」让大总管纠正一次又撤回；「过预算」可以读反；p1/P1 撞名；同一代价出现三个数。
3. **规则 13：只用中文**。39% 的助手轮次是全英文，两份收尾报告连待拍板题都是英文。
4. **STE 外：拍板题要翻成人能感知的后果，技术题不交给人**。产品派 P0；一次 11 题。
5. **规则 10：区分事实和推断**。推断被钉进测试、写成定论，后来 3 次 P0 级更正。
6. **规则 6：默认值和条件写清楚，各题默认值不互相矛盾**。三个会话的默认值组合起来会越过已有决定，或让核心功能停摆。
7. **规则 12：用具体数字代替程度词**。「3–5 倍」「确定变差」「明显弱一档」。
8. **规则 7 和 4：不堆名词，一句一事**。句长不超，但概念密度过高（「STFT/OLA、state、4 帧对齐」写在一句里）。
