## 规则 1：一词一义，同一事物始终同一叫法

**违规次数估计**：约 25 处（同一概念换 2–4 种叫法）。

**例子**
1. 05ea4065:465 表头写「CI 上实际跑的替身（真 Engine + 参考降噪器）」，同一会话 :145 叫「参考降噪器」，大总管叫 `ref`（:155），审查叫 `Ref`。人看到「替身」「参考降噪器」「ref」三个词，无从知道是同一个东西。
2. 吃字这个概念的叫法：「吃字」「吃词首」「主人误压」「句首被压」「句首误压」「被压超过 3 dB」（13ca618e:619、:633；e2a46d40）。英文会话里又叫 "word-dropping count"（0a8c2bd9:123）、"changes words"（da8efa6a:243）。
3. 「名额」「重活名额」「quota」「slot」「heavy-work slot」混用（13ca618e:167/187；0a8c2bd9:118）。同一会话里中英两套叫法都有。
4. 「盲听页 / 听测目录 / 对照页 / A/B page / comparison page / listening test」指同一类产物（13ca618e、0a8c2bd9:124、da8efa6a:235/249）。

**对人造成困惑的证据**
- 没有人直接问「替身是什么」，因为人不在这些会话里。
- 间接证据：sota 的产品派审查明确报了「术语太多」（da8efa6a:197）。05ea4065 的审查者也要先把「V-VACUUM 和 V-NR 算的是同一个数」拆开解释（:217）。同一个量有两个名字，结果它被拿去和基线比，方向还反了，变成一个 P0 缺陷。

**建议写进 CLAUDE.md**：「同一事物从头到尾只用一个中文名；首次出现时写清它指什么，之后不换同义词。」

## 规则 2：不对人用未定义的缩写、编号、自造标签

**违规次数估计**：对人的 5 份收尾里约 60 处；全部 12 份里超过 200 处。

**例子**
1. 05ea4065:459–494（给人的收尾）里，下列标签都没定义：
   - CI 层、QA 层、verifier、回归集、能力集、防作弊探针、门禁
   - R17、V-ONSET、L0、L1、定标
   - SIG / BAK / OVRL
   
   例句：「定标……没有一条 verifier 达到 L1，感知类全是 L0。」人不知道 L0/L1 是什么，这句话对人没有信息量。
2. c9f037a8:240–242：「**结论**：按 D38 分两层做……空闲时才更新权重，由小到大三档：归一化统计 → 归一化层的仿射参数（约 4.8K 个）→ 小适配器。」
   - D38 只给编号，不给内容。
   - 「仿射参数」「小适配器」都没解释。
   - 用「→」串联，屏幕阅读器会读成「右箭头」。
3. 13ca618e:623：「给 10 ms 实时回路加 0 ms，D32 的 45 ms 上限不受影响。」人要自己记得 D32 是什么。
4. da8efa6a:247：「Also: what did your earlier answer "5" mean?」人之前给过一个「5」作答，助手看不懂。这说明更早的提问里编号太多、指代不清，人的回答也随之含糊。这是双向沟通失败的直接证据。

**正面例子**：d103748c:158 写「声纹（认人的声音特征）」；:162 写「波束成形（用多支麦克风对准说话人）」。首次出现就在括号里用白话解释。整条收尾几乎没有 D 编号。

**对人造成困惑的证据**
- 「5」的歧义（da8efa6a:247）。
- sota 产品派审查：「术语太多、篇幅太长」（da8efa6a:197）。
- c9f037a8 的意图审查（:111）发现，助手把「主体是记参数，不是改权重」写进定调句，几乎就是人在 D36 否掉的那句话。助手只引用 D 编号、不复述内容，连自己都偏离了人的决定。

**建议写进 CLAUDE.md**：「对人说话时不用 D/P/R/V-/L/exp 编号或内部标签；必须提到时，先用一句白话说出它的内容，编号放括号里。」

## 规则 3：句子要短（指令约 35 字以内，描述约 45 字以内）

**违规次数估计**：对人的收尾里约 40% 的句子超过 45 字；最长的超过 90 字。

**例子**
1. 05ea4065:136（70+ 字，含 3 个分句、2 个英文词）：「`vdn-eval` 已写完并通过 clippy，但还没构建、没跑测试，也没跑过评测，所以 CI 层现在有几条 verifier、当前 main 过不过，都还没有答案。」
2. 05ea4065:474（约 75 字，被动句加名词串）：「根因：门控里的底噪估计，被模型输出在停顿里的瞬间低谷压得太低，结果 46% 的停顿帧被当成人声，再加 150 ms 拖尾，门控 82% 的时间开着。」
3. d103748c:162（约 60 字）：「它会加多少延迟、会不会超 45 ms、控制中心会不会列出我们这种菜单栏程序，都还不知道，要做实验。」
4. da8efa6a:242（英文 60+ 词）："It's very strong for offline post-production, but not first in any comparison we found. Those comparisons were run by audio magazines and are hearsay-level evidence, and all of them used RX's best offline mode. Its real-time version is about 43 ms in RX 11, and one user measured 85 ms in RX 12, over our 75 ms entry limit."

**对人造成困惑的证据**：没有直接追问。但人用 VoiceOver（cbc3062d:35）时，长句要整句听完才能抓住主干，代价更高。

**建议写进 CLAUDE.md**：「每句只说一件事，中文一句不超过 40 字；超过就拆句。」

## 规则 4：一句一个主题 / 一条指令

**违规次数估计**：约 30 处；在「待你拍板」里最集中。

**例子**
1. da8efa6a:247：「Run the delay-perception test next batch? Recommended yes, and that's also the default. Also: what did your earlier answer "5" mean?」一条决策题里塞进一个无关的追问。
2. d103748c:169：「认好你的声音后，『只留我』是否默认开。建议开，但会议室识别的实验过关前先默认关。」建议「开」和默认「关」放在同一条里，人读完不确定到底推荐哪个。
3. c9f037a8:244：「另外，不走 App Store 渠道发布的软件，很可能拿不到 Apple 收集的崩溃报告……」放在「找长尾问题」的子弹里，主题已经换了。

**建议写进 CLAUDE.md**：「一个列表项只放一件事；补充问题另起一项。」

## 规则 5：主动语态，主体清楚

**违规次数估计**：约 20 处「被……」句，或省掉主语的结论句。

**例子**
1. 05ea4065:474：「底噪估计，被模型输出在停顿里的瞬间低谷压得太低」。主体是「门控的底噪估计算法」，句子却把它写成受事。
2. 13ca618e:618：「保守版除一段外，都比只有 GTCRN 还响。原因是它在有人声时混回一部分原声。」这句主体清楚，可作正面例子。
3. c9f037a8:238：「所有改动都由自动提交 hook 提交到本分支，我没做任何 git 写操作。」主体清楚。但这类免责声明在 6 份收尾里重复出现，对人是噪音（见「其他问题」）。

**建议写进 CLAUDE.md**：「写成『谁做了什么』，少用『被』字句；结论句要有主语。」

## 规则 6：指令用祈使句，条件放前面（「如果 X，就做 Y」）

**违规次数估计**：约 10 处；多数给人的选项本身是好的。

**例子**
1. 正面：cbc3062d:39–42 的三选一：「**等它跑完**……」「**先暂停一部分，进度不丢**：比如用 `kill -STOP <PID>`……」动作在前，后果写清。
2. 反例：c9f037a8:248：「需要人定的 3 件事（见 decision.md 第五节；不回复就按建议做）」。条件「不回复」藏在括号里，后果是「默认推翻 D38」，而这条后果没有写出来。意图审查把这一点判为 P0（:111）：「人不回复，D36/D38 定下的『用着用着更新权重』就会被悄悄推翻」。
3. 反例：d103748c:169，条件「会议室识别的实验过关前」放在句末。

**建议写进 CLAUDE.md**：「给人选项时先写条件再写动作；『不回复就默认 X』必须单独一行写明默认会造成什么。」

## 规则 10：区分事实与推测

**执行得最好的一条**，正面例子最多。
- d103748c:155：「估算你的声音能高出约 20 dB，这是按距离算的，还没实测。」

## 规则 12：用具体数字和单位，不用「更好」「略」「一些」

**总体执行得好**（数字密集）。但有两类问题。

1. **数字前后矛盾**：05ea4065:473 写「门控 99% 的时间开着」，下一行 :474 又写「门控 82% 的时间开着」。没说明两个数各自的条件，人无法判断哪个对。
2. **数字有了，但没有比较基准**：13ca618e:614–616 的「−0.6 ~ −5.6 dB」没说多少算好；cbc3062d:27 写了「10 核的机器负载超过 10 就开始排队」，这是正面例子。
3. **模糊词**：d103748c:155「背景会比现在略吵」；13ca618e:602「效果小」（后文有数字补救）；c9f037a8:259「主目录的 `.42cog/intent.md` 好像有没提交的改动」。

**建议写进 CLAUDE.md**：「每个数字都写单位和比较基准（及格线或对照组）；同一个量的两个数并列时，写明各自的条件。」

## 规则 13：中英混排 / 整段换语言

**违规次数估计**：

- 中文句子里夹英文术语，而且有现成中文说法的：约 100 处，如 clippy、release、hop、build、workflow、worktree、slot。

**例子**
1. da8efa6a 全程英文（21/21），包括 3843 字符的给人收尾。可人用中文提问（:79「或者说我觉得看下来其实rx做的是最好的」），回答却是 "**Is RX the best?** It's very strong for offline post-production…"
2. 0a8c2bd9:132：「I sent the coordinator "abtest 已停" ("abtest has stopped")」。同一句里中英互译。
3. 13ca618e 的进度行中英来回切换：:78「Now the crate manifest and core modules.」、:84「正在写声纹提取（ONNX）模块」、:213「Add a no-alloc test for the realtime stages, then release build.」。
4. 05ea4065:136：「`vdn-eval` 已写完并通过 clippy……CI 层现在有几条 verifier、当前 main 过不过」。

**对人造成困惑的证据**：没有直接投诉。但 sota 这份英文收尾里出现了「5 是什么意思」的反问；产品派审查也报了术语多、篇幅长。屏幕阅读器读中英混排时要来回切换语音引擎，体验更差。

**建议写进 CLAUDE.md**：「跟人说话一律用中文；有中文说法的词不用英文，代码名用反引号标出。」

## 不在 STE 里、但造成困惑的问题

1. **一次抛出太多决策题**
   - 题数：multitalker 6 题（d103748c:166–172），p2 4 题，evalimpl 4 题，sota 4 题外加 1 个追问，ondevice 3 题。
   - 后果：sota 收到的回答「5」含义不明（da8efa6a:247）。
   - 「不回复就按建议做」的默认值差点悄悄推翻人的决定（c9f037a8:111，P0）。
   - 项目自己的 decision-batching 规矩是每批 ≤4 题，multitalker 超了。
2. **结论埋在后面**：sota 先列 Top 5，人的两个问题排在第 6、7 块（da8efa6a:232–244）。
3. **收尾报告太长**
   - 长度：sota 3843 字符，evalimpl 1731 字符，其余约 1100 字符。
   - 内容里混着给大总管的流程信息：「hook 自动提交」「我没做 git 写操作」「名额」「14 agents instead of 12」「5 行以下改动没触发」。人不需要这些。
   - 「我没做任何 git 写操作」这类免责声明在 6 份收尾里重复出现。
4. **把内部过程当成结果汇报**：例如「3 个对抗视角各自审了一轮」「Workflow 跑完」。人关心的是结论有没有变，不是审了几轮。
5. **读者错位**：同一份收尾既写给大总管又写给人，「你」有时指人，有时指大总管。c9f037a8 写「需要人定」，13ca618e 写「要你定」，人称不统一。
6. **给人 shell 命令**：cbc3062d:41 的 `kill -STOP <PID>`。好在只是举例，并且最后问「要我帮你暂停哪几个吗？」，把动手权留给了人。这一点是正面的。
7. **报错占位**：b8014977、e2a46d40 里有 4 条 assistant 消息只是「API Error: Your computer went to sleep」，没有恢复说明。这不归 STE 管，但人看到会以为任务坏了。
