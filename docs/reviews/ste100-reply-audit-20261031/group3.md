手下的收尾报告最终会经大总管转给人，报告里也直接用「你」称呼人，所以这些报告算面向人的文字。

## 规则 1：一词一义，同一事物始终用同一个词

**违规次数估计**：高，约 25–35 处，跨 5 个会话都有。最严重的是一个标签有多个意思。

**最有力的例子**
1. **「P1」一词四义**：
   - 4dcd5f33 中，P1–P4 是「预判」。见 :155「P1（插件和推理分进程、走共享内存）」，以及 :188、:228。
   - 4dcd5f33 :464 起，P1 又是评审严重度：「产品派审出 3 条 P1」（:483）。
   - 878b2dbe 中，P1–P4 是阶段：「§2.3 P1 行」「P1 阶段只剩 xtask」（:373、:469）。
   - 同批还有一个手下会话名叫 `p1`（878b2dbe :31、:103）。

   **后果**【审】：维护派指出（878b2dbe :338），「规约 §2.3 用 P1–P4 阶段当触发，而 decision.md 用 M0–M3，两套里程碑名没有对照表」，拆 crate 的触发条件因此读不出来。
2. **同一个 UI 选项换了三个名字**：「差不多」「分不出」「same」。
   - 3f8799ec :502 记录了首屏的写法：页面首屏叫人「拿不准选差不多」，可劣化检验题把答「差不多」判成不通过。
   - 51f228c8 :576 记录了改名：「"can't tell" (分不出) button replaces "about the same" (差不多)」。

   **后果**【人】：人在「全同」检验题上没过，选了 C（3f8799ec :885、51f228c8 :640），整轮结果因此降级、不能定档。说明文字和判分规则不一致，评审判为 P0。这不能证明人没过就是措辞造成的，但措辞是已知的风险源。
3. **同一概念的多种叫法**：
   - 揭盲表 / 对照表 / unblind-key / manifest（3f8799ec :575、:636、:774）。
   - 吃字 / 删除率 / del_rate / word loss / dropped words（3f8799ec :780；51f228c8 :456、:522）。
   - 送原声 / 原声旁路 / 旁路 / bypass（4dcd5f33 :602；878b2dbe :529–:539）。
   - 候选 / 模型 / 实现 / 槽位（3f8799ec 全篇）。
   - 名额 / 重活名额 / quota（3f8799ec :76、:102、:327）。
4. **「不可妥协 / 命门」被悄悄改写**【审】：4dcd5f33 :464 记录，命门比草稿多了一句，人还没拍板，卡片却已经按选项 A 写进「不可妥协」，和待拍板表自相矛盾。

**人困惑的证据**：人在检验题上失格（见例 2）。其余证据都是【审】。

**建议写进 CLAUDE.md**：同一件事全程只用一个名字；改名时写一次「旧名 → 新名」，并且不要让一个编号（如 P1）同时指严重度、阶段、预判或会话名。

## 规则 2：不用未定义的行话、缩写、自造编号

**违规次数估计**：
- 收尾报告里约 15–20 处。
- 交付文档里很多，评审逐项列出了 30 多个术语。

**最有力的例子**
1. 51f228c8 :239，产品派评审 decision.md：「术语太密：V1–V8、L/C/N/H 编号、D01/D10/D13/D28、G2、M5、Xeon、RTF、PESQ、WER、DNSMOS、lsnr、③/①、P.800……Bonferroni、IRL、ESTOI、LTASS、PSE、TSOS」。评审建议列名改白话，并在开头加 5 行词表。
2. 878b2dbe :347，维护派：「§0 对不熟 Rust 的主人读不懂。没解释的术语有：crate、trait、hop、Send、静态分发、enum、malloc、mutex、ort、AST、clippy、cargo-deny、xtask、tidy、RTSan、CI、IO 回调。」
3. 8dc56f15 :231，assistant 的原句：「无事实性 P0；实现派和产品派各指出一个结构性 P0：单轮降级会把 verifier 全降光、片段级相关会被片段难度带偏、RL 刷分查不出来」。一句里叠了 P0、verifier、降级、片段级相关、RL。
4. 4dcd5f33 :596–:606，收尾报告给人。正面的地方：括号里解释了「工作组（Audio Workgroup）」「临时签名」。问题：仍有「开发期（M0–M2）」「命门 1」，这两个词没有定义。

**正面例子**：

- 3f8799ec :778「背景噪音压得好不好（DNSMOS 评分）」「字听不听得清（可懂度）」，先说白话，后给术语。

**人困惑的证据**：没有人直接问「什么意思」（人不在这些会话里）。【审】两次把这一条列为 P1 或 P2。

**建议写进 CLAUDE.md**：对人写的文字里，每个缩写、编号（D01、P0、M0、V-*）和英文术语第一次出现时，用一句白话说明它是什么；能用白话说的就不用编号。

## 规则 3：句子要短（指令 ≤35 字，描述 ≤45 字）

**违规次数估计**：低。按纯汉字计，超过 45 字的句子每个会话只有 0–2 句。手下的回复多用短句加列表。

**例子**
- 8dc56f15 :231，上面那句约 150 字符（含英文），里面有 4 个从句。
- 3f8799ec :780：「三个模型都比原声多吃字。GTCRN 最少，FastEnhancer-M 最多。不过差别只有几个到十几个词，而且音量差 0.03 dB 识别结果就会变，所以真假要靠人耳判断。」最后一句串了 3 层因果，可以拆开。

**人困惑的证据**：无。

**建议写进 CLAUDE.md**：每句只说一件事；一句超过约 40 个汉字就拆成两句。

## 规则 4：一句一个指令或话题

**违规次数估计**：中，约 8–10 处。集中在把几个决定捆在一题里。

**例子**
1. 51f228c8 :463，第 3 条决定：「When a candidate is cut, and whether to keep the "usable / borderline / not usable" question」。两个决定放在一题里。

**建议写进 CLAUDE.md**：一个拍板题只问一件事；代价不同的两件事拆成两题。

## 规则 5：主动语态，写清谁做什么

**违规次数估计**：中，约 10 处。常见的是没有主语的「已记录」「已处理」「已提交」。

**例子**
- 4dcd5f33 :169「已记录。」没说记在哪、谁来用。
- 3f8799ec :836「这处 README 改动已自动提交（df4ef07），还没推送，大总管知道。」谁该推送没写明，要靠上下文推断。
- 正面例子：3f8799ec :771「后来我重建页面时把它的揭盲表覆盖了，清理文件时又删了它用的音频」，直接认责，主语清楚。

**人困惑的证据**：无直接证据。

**建议写进 CLAUDE.md**：报告动作时写明谁做的、结果放在哪里（如「我把 X 写进了 Y」），不要只写「已处理」。

## 规则 6：指令用祈使句，条件在前

**违规次数估计**：低。手下回复里，「如果…就…」的条件句多数放在前面。

**正面例子**：
- 51f228c8 :573「If you set the latency limit (D01) at 45 ms, GTCRN and FastEnhancer-M qualify. At 75 ms, DPDFNet-2 qualifies as well.」
- 51f228c8 :452「Open `dryrun-exp003.md` only after you've done the listening session.」祈使句加理由。

**反例**：4dcd5f33 :608 先描述实验，最后才说「所以需要你批准」，请求放在了段尾。

**建议写进 CLAUDE.md**：要人做的事写成祈使句，放在段首；有前提时写「如果 X，请做 Y」。

## 规则 8：段落短、一段一个话题、首句点题

**违规次数估计**：低到中。收尾报告大多用粗体小标题，首句就是结论，这点做得好。

**正面例子**：
- 3f8799ec :876「结论：这一轮你的耳朵和机器分方向相反。」第一句就给答案，后面跟表格和理由。
- 51f228c8 :631「The ranking is GTCRN first, FastEnhancer-M second, DPDFNet-2 last, but no gap is strong enough to count as settled.」

**反例**：
- 51f228c8 :203 的中期汇报用了一个过早的标题「GTCRN is ahead」。
- 【审】在 :224 指出，「GTCRN 领先 22/25」只用了轻快这一把尺子，会误导决定。
- 首句点了题，但点错了（见规则 10）。

**建议写进 CLAUDE.md**：每段第一句就是结论；结论只基于部分数据时，第一句就写明「只看了 X」。

**违规次数估计**：违规很少，是正面做法。

**正面例子**：

## 规则 10：区分事实与推断，区分建议与已定

**违规次数估计**：
- 手下自己的回复里，这条做得比较好：常写「大概率…但还没实测」。
- 交付文档里约 10 处把推断或建议写成了定论，均由【审】查出。
- 这是本组影响最大的问题之一。

**最有力的例子**
1. **把建议写成已定**：
   - 4dcd5f33 :483，assistant 承认：「卡片在人还没拍板时，就把我建议的选项写成了已定」。
   - 51f228c8 :226，产品派：「6 道题的『默认』全都等于『我的建议』……作者不拍板就等于 AI 替他定了」。
   - 8dc56f15 :220（产品派 #9）：「『我放弃什么』把『工业级』重新定义成『方法对齐、经作者定标』。这是改了人的原始目标」。
2. **过早下结论**：
   - 51f228c8 :203 给人和大总管写了「Using only data we already have…GTCRN is ahead」。
   - 【审】判为 P0：论文 PESQ 显示 GTCRN 最差，只用 25% 权重的那一把尺子就下了「领先」。
   - 后来人的听测结果确实是 GTCRN 排第一，但当时那是没有依据的结论。
3. **推断标成事实**：
   - 4dcd5f33 :506–:508，怀疑派指出：「『插件崩溃大概率只掉本设备』……是推断」「『BlackHole 证明这个形状在 macOS 27 上能用』……都没验证过」。
   - 3f8799ec :515，「README 说『全面领先』过头」。
   - 3f8799ec :601，「『可懂度全面领先』说过头」。

**正面例子**：
- 4dcd5f33 :601：「崩溃大概率只让这个虚拟麦克风掉线，但还没实测。」
- 51f228c8 :644：「I only saw that after the answers were unblinded, so I haven't changed this round's verdict」，写明了时间先后和偏差风险。

**人困惑的证据**：【总】大总管在 4dcd5f33 :58 强调「取舍卡『需要你拍板』一栏仍不许代填」，说明这个风险被反复提醒过。人自己的反应没有记录。

**建议写进 CLAUDE.md**：每条结论标明是「实测」「读源码或文档」还是「推断」；人没拍板的事一律写「建议，待你定」，不写进正文当既定事实。

## 规则 11：警告放在步骤之前，并写明后果

**违规次数估计**：少，但出现了本组唯一一起实际伤害到人的事故。

**最有力的例子**
1. 3f8799ec :575，大总管急问：「人在旧版页面（build …68ab，两候选）上答了 6 题，你重建 VoxLock 版时同路径覆盖了 manifest.js 和 unblind-key.json，旧揭盲表没了。」
   - 事故经过：assistant 在 :423「直接把模板拷成 index.html」之前，没有警告「人可能正在用这个页面」。
   - **后果**【人】：人答的 6 题只恢复出 3 段，揭盲了 2 题。人为此新定了一条规矩（:636，人原话）：「这种时候每次的对照表等等等任何东西，都要git commit」。
2. **正面例子**：
   - 4dcd5f33 :608，请求批准插件实验时先写后果：「做的时候全机会断音几秒，而且越过了本批不碰系统音频的规矩」。
   - 4dcd5f33 :607，「要输一次密码、重启一次电脑」。

**建议写进 CLAUDE.md**：覆盖、删除或重启人可能正在用的东西之前，先写一句「⚠️ 这一步会让 X 丢失或中断」，并给出不覆盖的做法。

## 规则 12：用具体数字和单位，不用模糊词

**违规次数估计**：中。手下的回复普遍给数字，问题出在估计值不断变化，以及少数「很轻」「大概率」「几个到十几个」。

**最有力的例子**
1. **听测时长估了 4 次，每次都改**，人据此安排时间：
   - 10 分钟（交代）。
   - 12–15 分钟：51f228c8 :334；3f8799ec :334。
   - 约 20 分钟：51f228c8 :457「it's about 20 minutes, not 10」。
   - 约 25 分钟：51f228c8 :527。
   - 最终约 19 分钟：51f228c8 :652。

   【审】在 3f8799ec :509 估算「14 屏要 25–35 分钟」，并指出：「时长改用实测：先自己计时听 2 屏再写数字」（51f228c8 :223）。
2. 4dcd5f33 :91「我先自己收集各仓库的维护状态和许可证（读本地，很轻）」。「很轻」没有量。
3. 3f8799ec :780「差别只有几个到十几个词」。区间太宽，判断不出算不算显著。

**正面例子**：3f8799ec :887「选『最清楚』的 11 次里有 8 次选 C，碰巧这么集中的概率不到 1%」。

**人困惑的证据**：【人】人最终没有按单次 20 分钟听，分了两天。时长估计连续改了几次，但没有记录到人对此的直接反应。

**建议写进 CLAUDE.md**：给人的时长、大小、代价写具体数字和单位；估计值要写依据（如「按每屏 100 秒 × 14 屏」），能实测的先实测再报。

## 规则 13：中英混写（本组的变体：整段用英文回复中文用户）

**违规次数估计**：本组最高。
- 51f228c8：42 个 assistant 回复全部是英文，包括给人的收尾报告和拍板题。
- 3f8799ec 有 16 个英文回复。
- 4dcd5f33 有 4 个，878b2dbe 有 5 个，8dc56f15 有 3 个。
- 同一会话里中英来回切换，例如 4dcd5f33 :423「Now `decision.md`.」、:441「Final self-review (common rule 11)…」、:519、:587。

**最有力的例子**
1. 51f228c8 :441–:466，整份给人的拍板清单是英文：「Four decisions for you… Weights for the three measures: I suggest clarity 40, naturalness 35, speed 25.」可人用中文工作，交代、大总管消息、人的原话全是中文。
2. 51f228c8 :576 引用页面的中文按钮时，只能写「"can't tell" (分不出) button replaces "about the same" (差不多)」：给人看的界面是中文，给人读的报告却是英文，还要反向翻译。
3. 3f8799ec :38「Both md5 match. Unzip into fresh dirs, then look at the scripts.」下一句 :44 又换回中文。

**人困惑的证据**：没有直接证据，人不在场。但项目的全部规约、交付文档都要求中文；51f228c8 的英文报告由大总管转述给人，多了一道转译。

**建议写进 CLAUDE.md**：对人和大总管的回复一律用中文；英文只用于代码、路径、专有名词，第一次出现时附中文。

## STE 未覆盖、但造成困惑或损失的问题

1. **人不得不问进度**【人】：3f8799ec :360，大总管：「人刚问『做好了吗』」。同时手下的现状页「还停在交接时（写着『没跑过』）」。手下没有主动更新状态，人只能来问。
   **建议**：每完成一个里程碑，就更新现状页并回报一句「做完 X，下一步 Y，预计 Z 分钟」。
2. **一次问太多题，默认值替人定了**【审】：
   - 51f228c8 :233「题太多，超过 4 题一批的规矩」。
