- **P1｜bench/src/main.rs:554 冷启动和内存的基线不公平**（第 1 轮 #1）
  - 核实：属实。计时前的 `prepare` 先完整建了一次 ORT 会话又销毁，之后才读「加载前」内存、再建会话；手写版没有这一步
  - 处理：README 结果节加 ⚠️ 说明：ORT 的打开时间和内存增量是第二次建会话的数，偏乐观；产品首次加载耗时估计不少于 `ort_env_ms`（约 17 ms），首次加载的内存没测，已列为待测。判据表里 `BE-COLD` 和 `BE-MEM` 的 ORT 一格都标了「偏乐观」或「不是首次」。待人拍板第 1 题的冷启动收益已注明含环境初始化
- **P1｜README.md:393 FE-M 去留仍按已废弃的口径判断**（第 1 轮 #2）
  - 核实：属实。3.8% 个核是连续跑的推算值，同一份 README 已经证明这种推算不可靠；按 D75，应看实际耗电和对其他程序的影响
  - 处理：一句话结论和待人拍板第 2 题改为「证据不足，先补测 FE-M 实时节奏下的耗电和干扰，再决定提不提『手写 FE-M』」；同一句已发给 applebe 改它那边的 standard.md 矩阵格（见下一轮核对）
- **P1｜bench/src/main.rs:691 对拍不过也不会挡住后面的测速**（第 1 轮 #3）
  - 核实：属实。旧版 `parity` 不论结果如何都返回 Ok
  - 处理：对拍加 `be_parity_pass` 字段，判据同 standard.md：没有值差 > 1e-3、没有非有限值，且 SNR ≥ 60 dB。不过就返回非零退出码，配合脚本的 `set -e`，后面的测速不会再跑。reset 检查不逐位相同也报错。已知会错的对照（tract 复用状态）加了 `--allow-fail`（`tools/run_bench.sh:41`）
- **P2｜bench/src/main.rs:583 实时节奏下的「超时帧」漏算了醒来迟到**（第 1 轮 #4）
  - 核实：属实。睡眠结束后才开始计时
  - 处理：新增字段 `late_p50_ms`、`late_p999_ms`、`late_max_ms`（醒来迟到）和 `release_p999_ms`、`release_max_ms`、`release_over_3ms`（从计划时刻到完成）；字段说明写明 BE-DEADLINE 应看 `release_over_3ms`。已有的数据都是旧字段，README 里的「超过 3 ms」都指纯推理耗时
- **P2｜bench/src/main.rs:685 失败时输出的不是合法 JSON**（第 1 轮 #5）
  - 核实：属实。`{:.2}` 遇到 NaN 或 inf 会原样打印
  - 处理：加 `jnum()`，非有限值一律写 `null`；对拍和 reset 检查的输出都改了
- **P2｜README.md:44 冷启动过线没有直接测量依据**（第 1 轮 #6）
  - 核实：属实。表里的数是用平均帧耗时推算的
  - 处理：判据表标「推算，未直接量」；新增字段 `open_to_warm_ms`，直接量从开始打开到预热完的时长
- **P2｜README.md:316 用算错的实现证明「新开状态几乎没有代价」**（第 1 轮 #7）
  - 核实：属实
  - 处理：改为只摆出两组观测值，并写明这组数不能用来算代价
